# Architecture

## 1. The billion pixels

| | |
|---|---|
| Grid | **40 000 × 25 000 = 1 000 000 000** cells (`src/lib/grid/constants.ts`, mirrored by CHECK constraints in SQL) |
| Why not 2:1 | 10⁹ = 2⁹·5⁹, so width/height = 2ᵃ·5ᵇ with *a, b odd*: 8:5 (40 000 × 25 000) or 5:2 (50 000 × 20 000) are the closest to a world map; 8:5 is used |
| Projection | **Web Mercator** (`src/lib/grid/projection.ts`): x linear in longitude, y = `(M(latMax) − M(φ))·Ry` with `M(φ) = asinh(tan φ)`. Conformal: countries keep their familiar shape at every latitude (an equirectangular map looks stretched near the poles). `Ry` fits the latitude band exactly into the 25 000 rows, ≈ 5 % below the horizontal scale `R = W/2π` (a Mercator 5 % flatter than a pure one, invisible). One pixel ≈ 1 002 m wide at the equator, ×cos(latitude) elsewhere |
| Coverage | lat **56.7°S → 83.8°N**: all of Greenland (83.67°N) and Chile's Diego Ramírez islands (56.5°S) fit; only Antarctica is cropped. Longitude **168.5°W → 191.5°E**: the map's edge lies in the Bering Strait, the one meridian that slices no country (only the Aleutian island of Umnak straddles it): Russia is whole at the east edge, Alaska starts at the west edge. **The world wraps horizontally** in the engine: the scene is drawn once per visible copy of the world (`offX = c·W`, used by `worldToScreen`/`visibleWorld`), the camera's x is taken modulo W, `screenToWorld` maps any point of a copy back to its real grid position (so hit-testing, selection and purchases are unaffected), and `flyTo` takes the short way round. On a window wider than the planet the continuation shows at the sides; the world is never closed by a frame on the left or right. Rings that straddle the map's own edge are emitted on both sides by the build script; polygons that the source data cut along the antimeridian (Chukotka, Fiji…) now meet in the middle of the map and their shared edge is never stroked (`outlineWithoutClipEdges(…, seamX)`) |
| Parcel | integer rectangle `(x, y, w, h)`, area ≥ 100, sides ≤ 1000, area ≤ 250 000 by default (admin setting; hard cap 1 000 000) |

The grid is **virtual**. Nothing ever materialises one object per pixel: only purchased rectangles are rows.

## 2. Rendering engine (why a custom Canvas 2D renderer)

The map is a flat 40 000 × 25 000 pixel plane (Mercator-projected geography on top of an integer grid). MapLibre/Leaflet are built
around tile pyramids of that same projection but would need bolt-on code for pixel-exact images and a grid of exactly 10⁹ cells; OpenSeadragon needs a pre-rendered deep-zoom pyramid of
the *whole* planet. A purpose-built engine (`src/components/map/engine.ts`) gives one coordinate system for geography, parcels
and overlays, nearest-neighbour pixel-exact zoom, touch/pinch/inertia, and no tile infrastructure.

Layers, by zoom (`scale` = screen px per grid px, 0.029 … 48):

| Layer | Source | Notes |
|---|---|---|
| Ocean, land, country borders | static vector data (`public/data`, Natural Earth) | rasterised **once per tile** into 512-px offscreen canvases, clipped per tile (Sutherland–Hodgman / Liang–Barsky) so a frame is a few `drawImage` calls. **Three levels of detail** picked from the zoom `k = ⌈log₂(scale·dpr)⌉`: 1:110m (k ≤ −2), 1:50m (k = −1), 1:10m (k ≥ 0) |
| Départements / states / provinces | Natural Earth admin-1 | internal borders only (arcs shared by two units of one country; the country outline comes from the country layer). Coarse simplified file `admin-lo.json` for k = −3…−1, 1:10m cells beyond; thin solid line. In metropolitan France the département borders are derived from the commune data instead, so they coincide exactly with the commune lines |
| Communes (France) | Etalab communes (simplified), via `gregoiredavid/france-geojson` | 35 228 communes → topology (shared arcs) → internal borders between communes of the same département, in 250-px cell files `geo/m-{cx}-{cy}.json` (≈ 40 KB each, 33 files), drawn from zoom k ≥ 4 (≈ ×8, when a commune is ~70 px wide; `COMMUNES_FROM_K`) as fine solid lines — and the chunks are only downloaded then. Other countries: add a source in `scripts/build-world-data.mts` (`chunkCommune` is country-agnostic) |
| Place names | countries, big cities (≥ 400 000, always loaded), admin-1 names (`admin-labels.json`, shown once the unit is wide enough to hold its name), cities 15 000+ (zoom ≥ 1.1×) and towns 1 000+ (zoom ≥ 6×) | greedy collision avoidance, most important first; localised (en/fr) for countries and admin-1; zoomed in, names sit under the parcels |
| 1-px grid | procedural, **land only** | the **only** grid: 1-pixel lines, shown in the last stretch of the zoom only (fading in from ×24 to ×30, the maximum being ×48; `gridAlpha` in `src/lib/map/pixelGrid.ts`). No 10 px / 100 px lines and no dot matrix at any zoom. Clipped to the land path of the current level of detail (`landPath`/`onLand` in the engine, cached while the camera stays inside it), so oceans and seas stay clean — they are not for sale |
| Parcels, scale < 1 | `/api/map/raster/{z}/{x}/{y}?v=` | 256-px PNG tiles composited by `sharp` from parcel images, z = 0…8, **immutable per map version** (CDN). From level 3 on (1/8 pixel or less per grid pixel) a parcel of at most 8 px on the tile is its **average colour**, its picture is not even fetched (`FLAT_FROM_LEVEL`); the pictures fetched are kept in a 48 MB in-memory cache of the server instance (a stored file never changes) |
| Parcels, scale ≥ 1 | `/api/map/tiles/{x}/{y}?v=` (JSON, 1000×1000 px) + `/api/assets/{id}` | only tiles in view; images loaded lazily, drawn with smoothing **off** so pixels stay razor sharp. The tile queue is **not** first-come first-served: a tile not wanted for 2 frames is forgotten, the nearest to the screen centre goes first (8 at once) — zooming from the world to a city crosses ~100 tiles nobody sees, which once left the final view empty for seconds. Until a tile arrives, the coarser rasters already in memory stand in for its parcels (clipped to that tile) |
| Hit-testing, collisions | the same JSON tiles | client-side convenience only; the database decides |
| Overlays | selection, preview of the buyer's creation, highlight | |

### Price per pixel

The unit of sale is the **pixel** (default **€0.50**, `app_settings.price_unit_cents = 50`, admin-editable; migrations 7 and 8 move the earlier factory defaults of 100 and 10 cents to 50 and leave any other price an admin chose alone). A parcel's surface is its number of pixels, and so is its price: two parcels of the same size cost the same wherever they are.

### Draw order on the map

Geography → (zoomed in) place names → **1-px grid** (land only, last zoom stretch only) → **parcels** (their drawing cut along the coast) → place names when zoomed out → overlays (selection, highlight). The grid is a guide to *free* land, so it sits under the parcels: a taken parcel shows its creation (or, while it awaits moderation, its neutral block) with no grid line across it (`tests/e2e/map-parcels.spec.ts` checks every pixel of a parcel).

### Drawing finer than a pixel (down to 0.1 px)

The grid does not change: a parcel is `w × h` **pixels**, those are what is sold, counted (`available`, `sold`) and priced (€0.25 each). What changes is how finely a creation is **drawn**: every pixel holds `k × k` dots, so the finest brush is `1/k` of a pixel — **0.1 px** when `k = 10`. The editor offers 0.1, 0.2, 0.5, 1, 2, 3, 5 and 8 px (those that are a whole number of dots at the parcel's precision).

* **Precision is capped by the size of the image**: `k` is the largest value ≤ 10 with `k² · w · h ≤ 4 000 000` dots (`creationScale()` in `src/lib/grid/constants.ts`, `px_dot_scale()` in SQL, tested to agree). A 20 × 20 or 200 × 200 parcel gets the full 10 × 10 dots per pixel; a 500 × 500 parcel (the default maximum area) gets 4 × 4 (0.25 px); a 1 000 × 1 000 one gets 2 × 2.
* A creation image is the parcel's size **times any whole scale from 1 to `k`** (`px_add_asset` and `processCreation` check it; anything else is `px_bad_dimensions`). Older creations (1× or 2×) stay valid. The asset rows keep the real image size.
* **The editor** works in dots, with a zoom (so that a tenth of a pixel is reachable) whose **1× always shows the whole parcel in the space available, whatever its size** (`src/lib/editor/zoom.ts`: the fit is measured from the width and the height, the next levels magnify from it, up to a dot of 48 screen pixels; the same on the shared drawing page), a pan tool, a flood fill on typed arrays and an undo whose memory is bounded (every snapshot is a full copy of the canvas). A very detailed picture that would exceed the upload limit (3 MB) is sent at half the precision, then half again.
* **Colours.** The text layer has **its own colour** (a block of its own in the text panel; it starts in the current stroke colour and is never changed by choosing a stroke colour, nor the other way round). The pencil can be a **multicolour brush** (`Palette.tsx`, shared by the editor and the shared canvas): switch it on, click colours to add or remove them (at most 8, never none; each shows its rank), and the stroke runs through them in order, **one brush width of each** and never less than a whole pixel (`strokeRun`, `mixColor` in `src/lib/editor/colors.ts`, unit-tested). The colour of a dot depends only on how far the stroke has travelled, so fast and slow strokes look the same; the eraser and the fill are unaffected (the fill uses the colour last picked). On the shared canvas every dot of a multicolour stroke is sent with its own colour. (`tests/e2e/editor-colours.spec.ts`, `tests/e2e/together.spec.ts`.)
* **Images are served at the size the screen needs.** `/api/assets/:id?max=N` (N in 64, 128, 256, 512, 1024, 2048) returns the creation shrunk (area-averaged, never enlarged) so that its longest side is at most N. The map engine asks for the size a parcel occupies on screen (and shows a smaller variant already in memory meanwhile), cards and thumbnails ask for theirs; the moderation queue and the editor load the original.
* The map shows dots crisply once they are magnified (≥ 1 dot per device pixel); a finer creation drawn smaller is averaged (canvas smoothing in the engine, lanczos in the server's raster tiles and OG images).
* "Draw together" works in dots too: its overlay is `k·w × k·h`, and a published snapshot is composed at that resolution (an older creation underneath is enlarged by nearest-neighbour, so nothing is invented). Migrations 10 and 11 convert overlays drawn at the previous precisions.

### Land and water are for sale — two categories, each pays for what it owns (migration 15)

A parcel is a rectangle with a **kind**: `land` (every parcel so far) or `water`. A **land** parcel owns the *land* pixels of its rectangle; a **water** parcel owns the *water* pixels of its rectangle. The other pixels are **cut away**: they are not the parcel's, they are not shown as its, and they are free (or discounted). Land and water never share a pixel, so a land parcel and a water parcel may sit on the very same rectangle. Admin settings (`app_settings`, editable in the back office):
* `min_land_percent` (default **50**): at least this share of a land parcel's pixels must be land (1–100).
* `sea_price_percent` (default **0**): a sea pixel cut away from a land parcel costs this % of a land pixel (0 = offered; 0–100).
* `min_water_percent` (default **50**): at least this share of a water parcel's pixels must be water (1–100).
* `water_price_percent` (default **100**): an owned water pixel costs this % of a land pixel (1–1000; 100 = same price).
* `land_cut_price_percent` (default **0**): a land pixel cut away from a water parcel costs this % of a land pixel (0 = offered; 0–100).

Price of a land parcel = `land × unit + ⌊sea × unit × sea% / 100⌋`; of a water parcel = `⌊water × unit × water% / 100⌋ + ⌊land × unit × cut% / 100⌋` (`quote()` in `src/lib/grid/pricing.ts`, the same integer arithmetic as `px_start_order`; the order stores `kind`, `land_px`, `sea_percent` (the percentage of the cut-away pixels, whichever kind) and `water_percent`, and `orders_amount_consistent` keeps the amount explainable from the row alone). The buy panel and the order summary show the split ("1 486 px of your parcel are sea, offered: you only pay for the 2 114 px of land"; for water: "…are land, offered: you only pay for the … px of water").

**Whatever a buyer creates on water is shown in three blues.** Customisation, moderation and payment are the same for both kinds; only the DISPLAY differs. `src/lib/images/waterTint.ts` (pure, unit-tested; palette light `#7fc8f0`, medium `#2f8fd8`, deep `#1b4f9c`, chosen by lightness) turns any picture into those three tints. The stored original never changes: `/api/assets/:id` serves the blue version to the public (tinted first, shrunk after), and the original to the uploader and the staff with `?raw=1` (the editor and the moderation queue ask for it); the server raster tiles, the metadata tiles' average colours, and the buyer's preview on the map (`tintedBlob`, `MapEngine.shownPreview`) use the same tints. **On the map, a water parcel is drawn a little see-through** (`WATER_ALPHA = 0.62` in `engine.ts`, applied to the whole water pass — the water raster layer and the per-parcel drawing alike, so nothing jumps when the zoom changes from one to the other): the sea shows through and the opaque cream of the land stands out against it. The parcel's own page, the cards and the thumbnails keep the full blues. (`tests/e2e/map-water.spec.ts` checks the pixel is the blue blended with what is under it, not the raw blue.)

**Display latency (measured on the production build, network 120 ms and processor ×4 slower; before → after):** the world view asked for 176 requests and now asks for 62 (the water layer is only asked for where `/api/map/water` says there is a water parcel; the raster level follows the DEVICE pixel, one level coarser on an ordinary screen, four times fewer tiles), and a zoom to Europe went from 320 requests to 100; the map was complete after 6.3 s and now after 3.9 s (8.5 s → 5.4–6.2 s with the story). Tiles of land and sea are made on a time budget per frame (`BAKE_BUDGET_MS`, at least one per layer), arrivals share a redraw (`invalidateSoon`, 60 ms), and the destroyed-sea tiles are prepared with the others while the map is idle. `?perf` in the address exposes the engine in production (`window.__pxEngine`) to measure the real build.

**One guarantee per kind.** `parcels_no_overlap` became two partial exclusion constraints, `parcels_no_overlap_land` and `parcels_no_overlap_water`; `px_is_area_free(…, kind)` and `px_start_order(…, kind)` take the kind (last, optional argument: every older call is a land purchase). `parcels.owned_px` (generated) is what a parcel really owns, whatever its kind.

**The destroyed sea is a plain lavender field** (scanlines only): the error colours (magenta, cyan, orange…), the sliding bands and the colour fringe along the edge of a destroyed area belong to the LAND alone. **While buying water the colours are swapped** (the water is cream, the land takes the colour of the sea); in both modes it is the water that is hatched, so that nobody mistakes one for the other.

**On the map**, water is drawn **under the land**: ocean colour → destroyed sea (story) → water parcels → land tiles (opaque on land, so the coast cuts every water parcel exactly, at every zoom, with no clipping) → land parcels (clipped to the land as before). The server's raster tiles have two layers (`/api/map/raster/{z}/{x}/{y}?v=` for land, `&k=w` for water). Hit-testing asks who OWNS the pixel under a point (`MapEngine.parcelAt` + `landAt`): the land parcel on land, the water parcel on water, so the cut-away part of a parcel is not clickable. While buying, the selection only collides with parcels of its own kind (`setBuyKind`), and the colours are swapped when buying water.

*Land* means: the pixel's centre is inside the Natural Earth 1:10m land polygons (even-odd) — the same data files the map draws (`public/data/geo/g-*.json`). `src/lib/geo/landmask.ts` scan-converts the polygons for just the window being asked about (no bitmap, no table of cells: a 20×20 parcel is one pass over the edges of ≤ 4 cells, a 1 000×1 000 one is still instant).
* **Server (authoritative):** `landServer.ts` counts the land pixels in `POST /api/checkout` *before* any pixel is held (→ 422 `px_not_on_land` below the minimum share) and passes the count to `px_start_order(…, p_land)`; the availability probe returns `landPixels`, `onLand` and the quote. PostgreSQL range-checks the count (1 ≤ land ≤ area, share ≥ `min_land_percent`), computes the price from `app_settings`, stores `land_px` and `sea_percent` on the order and `land_px` on the parcel, and the `orders_amount_consistent` constraint keeps the amount explainable from the row alone. The cells are cached in memory (24, LRU) and `outputFileTracingIncludes` ships the data files with the serverless functions. The land count itself is trusted from the app server (PostgreSQL has no map); `px_*` functions are not callable by browsers, so the HTTP routes are the only way in.
* **Browser (courtesy):** `Geo.landIn` gives the buy panel an instant answer (`water` state below the minimum share, red selection and dashed ghost, live price); while buying, the sea is hatched under the land tiles.
* **Counters:** `px_public_stats()` sums `owned_px` — every pixel owned, land and water — against `TOTAL_PIXELS` (the whole 40 000 × 25 000 = 10⁹ grid): *sold / planet*, *available = planet − sold*, with the water share on its own (`water_pixels`, `water_parcels`). The 308 046 591 land pixels (30.8 %, `npm run data:world` → `src/lib/geo/landPixels.ts`) are only used to price and count the cut.
* **The drawing is cut along the coast.** The parcel stays a rectangle (that is what is chosen, bought and priced), but on the map only the part of its drawing that lies on its own kind of pixels is shown: the engine clips land parcels (and the editor's "Preview on the map") with the same land path as the grid, so the sea stays sea; water parcels are cut by the opaque land drawn over them. The parcel's own page, card and share image show the whole drawing. Covered by `tests/e2e/map-parcels.spec.ts` (a coastal parcel shows its drawing on ≈ 53 % of its rectangle, the land share, and the sea elsewhere).
* Parcels bought before the rule existed have `land_px = NULL` (= all land) and are untouched.
* Lakes: only what the 1:10m land layer cuts out is water (the Caspian); ordinary lakes (Victoria, Baikal, the Great Lakes…) are land in this data. Adding Natural Earth's lakes layer would change that.

### "100 days to save the world" (art direction Glitch)

A story laid over the site, chosen among three mock-ups: a countdown to the (fictional) destruction of the digital world, after which the land nobody has acquired is shown as destroyed and the acquired parcels survive. **It changes how the site looks, never how it works** — buying, parcels, accounts and moderation are untouched, and every figure shown is a real one.

* **Off unless configured.** `NEXT_PUBLIC_WORLD_END_AT` (an ISO date with its time zone) is the end of the world; without it nothing of the story exists on the page. **`?preview=J-9`** (`J-87`, `J-3`, `0` for the end, `off` to forget) simulates a moment for looking at any chapter; it counts down in real time from where it was opened, says "PREVIEW" on the plate, and follows the visitor from page to page for the tab (`sessionStorage`).
* **The clock** (`src/lib/doom/clock.ts`, pure and unit-tested): days/hours/minutes/seconds left, the **five chapters** (J100→J76 *the message arrives*, J75→J31 *first cracks*, J30→J8 *it speeds up*, J7→J0 *last week*, then *the end*) and `infection()`, the share of the unacquired land the story has corrupted (about 4 % at J-87, 48 % at J-9, all of it at the end — the pace the map layer will follow). `useDoom()` (`components/doom/useDoom.ts`) shares one 1-second clock between all the parts and renders nothing on the server or before mount.
* **The parts** (`components/doom/Doom.tsx`, styles `.doom-*` in `globals.css`, colours `--color-glitch-*`): a scrolling hazard strip above the header (`DoomTicker`, decorative, `aria-hidden`), the countdown plate on top of the map (`DoomPlate`, `role="timer"`; hidden while a parcel card or the buy panel is open), the sentence of the current chapter under it (`DoomMessage`; at the end: *"The world has been deleted. N plots survived."* with the **real** number of parcels), the counter card told in the story's words (`DoomStats`: "World saved", the real share of the land acquired, an ordinary progress bar with its two ends named, and "still in danger"), the countdown plate kept small (380 px wide, digits of 2.9 rem at most) so that it leaves the map in view, the "Latest creations" tile renamed "Latest rescues", and the call to action ("Find your spot" → "Save my plot", then "Join the survivors"). English and French in `messages/*.json → doom`.
* **Care for people.** `prefers-reduced-motion` stops the strip and the stutter; the digits stutter once a second for a tenth of it (far under 3 flashes per second); the text keeps WCAG AA contrast (cyan and magenta are only ever fringes, never running text); axe passes at the start, in the last week and at the end (`tests/e2e/doom.spec.ts`, and a phone check in `mobile.spec.ts`).
* **The corrupted land on the map** (`src/lib/doom/corruption.ts`, pure and unit-tested; painted by `MapEngine.paintCorruption`). A large-scale noise field (blobs of 800 to 4 000 px, wrapping at the antimeridian) gives every place a **rank among the land**, calibrated once on the coarse coast (`Geo.landLattice`): so "intensity 30 %" really is 30 % of the land, whatever the continents' shape, and the corrupted area only grows. A cell is damaged when its rank is below the intensity (`damage`, with a ragged edge); the intensity is `infection()` of the clock (`MapShell` → `engine.setStory`, in 0.5 % steps). It is painted **into the geography tiles**, between the land fill and the borders, inside the land only: big square cells of constant size on screen (4 device px at 1×, more on dense screens, so a tile holds a whole number of them), scanlined lavender (clean: the small multicoloured squares that used to be scattered over it were removed at the owner's request; only the very first cyan/magenta sparks at the leading edge remain), cyan/magenta fringes at the edge of the destroyed area, bands that have slid sideways, a little transparent when zoomed right in (`levelAlpha`) so that the land stays legible for buying. Whole 8 × 8-cell blocks that are untouched or fully destroyed are skipped or filled in one go (tile bake 3–10 ms, a frame stays 1–3 ms). A tile of another step of the story is redrawn lazily while the old one stays on screen, so nothing flashes. **The coasts of the destroyed land come apart into colours** (`MapEngine.paintCoastFringe`, `destroyedRuns` and `fringeShift` in `corruption.ts`): once the coast line is drawn, a cyan echo of it slipped to the left and a magenta one to the right (white where they overlap) are made on a reusable tile-sized layer and copied over the coast **only where the land is destroyed** (runs of 8 px rows of the tile found from the same ranks as the corruption, so intact land keeps a clean coast), a few bands of 16 px slid sideways like the torn bands; zoomed out it is a thin, tight edge (`fringeLook`: echoes 1 px from the coast, no sliding bands — a wide fringe turned the coasts into a tangle of parallel lines when the whole world is on screen), spreading and sliding as one zooms in; it fades with `levelAlpha` when zoomed in, is part of the end-state tiles of the final sequence, and costs about 2 ms per tile on top of a tile's 3–10 ms (software rendering, best of several runs; the strips are copied in as few calls as possible: copying them one by one cost several times more). Parcels are drawn after the geography, so **the acquired parcels stay intact**; during the story each is framed in white and orange.
* **The bug of the destroyed land, every 30 s** (`src/lib/doom/glitch.ts`, pure and unit-tested; `MapEngine.glitchNow/drawGlitch`). For about 1.3 s the destroyed zones tear sideways in bands — borders, scanlines and the cyan/magenta coast fringes slide together, by up to 44 tile px, a new still picture every 90 ms (a stutter), with a power that rises and falls so that it starts and ends softly — then everything is back exactly where it was (pixel for pixel: `tests/e2e/map-doom.spec.ts`). **Nothing is baked**: each geography tile keeps the destroyed runs it was painted with (`GeoTile.glitch`) and, during a burst only, those runs are drawn again over the tile, slid (`drawImage` of bands, merged when neighbours slide alike), so the cost is zero between bursts. The sea, the acquired parcels, the labels and the interface do not move. Off for an ordinary map, before anything is destroyed, during the final sequence, in a hidden tab and for `prefers-reduced-motion`. The timer starts when the story starts (so the first burst comes 30 s after opening the page); `engine.setGlitchEvery(ms)` and `engine.glitchNow()` exist for the tests.
* **The story tile** (`DoomPlate` in `components/doom/Doom.tsx`, placed by `MapShell`). One small card at the top of the map — the plate's hazard-striped header, the title "Save the world. And the pizza with it." on **one line** (`doom.titleA/B`; its size follows the tile's width through a container query, `cqw`, so that it never wraps in either language from 320 px up: it saves a line of the map), the countdown, and two buttons ("Save my plot", "Read the story") — instead of several floating pieces, so that the map stays as visible as possible (chosen on mockups; the paragraph of the mockup and its two pixel drawings were dropped). The sentence of the current chapter is **for screen readers only** until the end (the strip above the header says the same things aloud); at the end it is shown again ("The world has been deleted…") with Replay and Share. After the end the title and "Save my plot" are gone (nothing can be bought): the tile is the plate and "Read the story".
* **The story** (`src/components/doom/Comic.tsx`, `src/lib/doom/comic.ts`, pictures `public/story/panel-1…8.webp`). A "Read the story" button on the story tile (only where the story exists) opens a modal `<dialog>` with **eight pictures, the owner's own** (hooded AI, burning Earth, Protocol ZERO, the last chance, the plots to protect, the creations to save), one at a time: arrows over the picture (Previous/Next), dots, ← → keys, swipe, Esc or a click outside closes it. **The window is exactly as big as what it shows** (no empty space): its width is the smaller of 62 rem, the screen's width and what the screen's height can show of a 16:9 picture (`(100dvh − 23rem) × 16/9`), and it is anchored near the top, so nothing moves under the visitor's finger when the caption changes. **A picture comes in with a wipe** (`clip-path`, 0.45 s): from the right when going on, from the left when going back, over the one that goes (kept under it for a moment); still for `prefers-reduced-motion`. There is no automatic reading (removed at the owner's request), and the last picture offers "Save my plot" (or "Meet the survivors" after the end). **The captions are part of the pictures, in French** (the owner's); the page also writes each one **as text under the picture, in the language of the page** (`messages/*.json → comic.panels.pN.text`, with a description of the picture in `alt`): readable on a phone, where the words of the picture are tiny, and translated for English visitors (the French in the picture stays French for them). The originals (1920 × 1080 JPEG, numbered in the order of the story) are in `assets/story-source/` and are **not served**; `npx tsx scripts/build-story.mts` turns them into the 1280 × 720 WebP files of `public/story/` (about 110 KB each). To change a picture: replace its original there, run the script, commit both. The dialog sets `pointer-events-auto` itself: it is rendered inside the countdown's `pointer-events-none` container and would otherwise inherit it (the e2e test caught this).
* **Acquired parcels are left alone.** They are drawn exactly as on the ordinary map, intact among the corrupted land: no frame, no marker from afar (the owner asked for nothing: an earlier orange frame and a beacon list, `/api/map/beacons`, were removed). (`tests/e2e/map-doom.spec.ts` checks that no orange is drawn around a parcel.)
* **The final sequence** (`lib/doom/finale.ts`, the pure timeline, unit-tested; `components/doom/finaleStore.ts`; `MapEngine.startFinale`). When the countdown reaches zero **in front of the visitor** (`useDoom`'s shared clock notices the crossing; a page opened after the end shows the end state without a show), or when they press **"Replay the destruction"** (shown after the end): one white flash (held for an instant, gone after 0.45 s, a single one that only ever fades), a **2.2 s shake** (smooth and heavy rather than a random jitter, up to 18 px and 0.45°, a little less on a phone; the canvas is moved with CSS and scaled up by just enough, `shakeZoom`, that its edges never show), then a low rumble under the whole sweep and three heavy impacts, and a **slow sweep** from west to east across the *screen* (whatever the camera looks at) from 1 s to 13.5 s, easing in and out. Ahead of its front the light dims (a shadow, creeping scanlines); the front is a wide band of cyan, magenta and white blocks of three sizes with a storm of pixels around it; behind it the land is the end state, bands of it slide sideways over 240 px with their colours slipping apart (harder at each impact), and bits of the world fall away. **The sweep erases every place name as it passes** (`labelPlan` decides which: whole ahead of the front, the ones it is crossing are cut at the front, those just behind tear away as cyan and magenta ghosts, the rest are gone; `MapEngine.drawLabels`), and **the end state has no names at all, for good** (a page opened after the end shows none; "Replay the destruction" brings them back to take them away again). The end state of the visible land is drawn **ahead** (`armFinale`, 2 tiles per frame, in the last minute, or taken from the tiles already shown for a replay), so nothing is made while it plays; at the end those tiles simply replace the map's (no redraw, no flash). While it plays the plate says "WORLD DELETED", the sentence says "ERROR 0x064 — DELETION IN PROGRESS" and nothing can be replayed; when the map has finished (`onFinaleEnd`) the interface says "The world has been deleted. N plots survived." and the call to action becomes "Join the survivors". With `prefers-reduced-motion` the end state only fades in (names included): no flash, no shake, no front. `?preview=T-5` makes the countdown end in five seconds, to watch it all live; `?preview=0` is the end state, with the replay button. (`tests/e2e/map-doom.spec.ts` steps through the sequence with a replaceable clock.)
* **The share image follows the story** (`src/app/api/og/home/route.tsx`, the pure part — which state, which words, which size — in `src/lib/og/story.ts`, unit-tested). Three states: the ordinary site (no end date configured: the old tagline, now in the pixel font), the countdown ("9 DAYS LEFT", the real number of days, on the plate with its cyan/magenta fringes) and the end ("THE WORLD HAS BEEN DELETED." and the **real** number of plots that survived, read from the database; nothing about the number if it cannot be read). The route works the state out for itself from `NEXT_PUBLIC_WORLD_END_AT` (an address cannot switch the story on: `&s=e` is only there so that the *address* changes and platforms that keep previews for days fetch a fresh image — the layout's `generateMetadata` adds it with the day), or from `?preview=` (same words as the site's preview). It is drawn in Jersey 10, the site's pixel font, read from `node_modules/@fontsource/jersey-10` (`outputFileTracingIncludes` in `next.config.ts` carries it into serverless bundles; Satori reads `woff`, not `woff2`); a text with fringes is three layers (a cyan copy, a magenta copy, the text), because one text-shadow only draws one colour, and every such line is sized by `fitSize` so that it stays on one line (the copies do not wrap with the text). After the end a **"Share" button** sits next to "Replay the destruction" (`DoomShare` / `DoomActions`): the device's share sheet where there is one (title, the sentence with the real number of plots, the home page in the visitor's language — never their preview), else the link is copied ("Link copied"). (`tests/e2e/share.spec.ts`.)
**Two currencies: euros in the euro area, dollars elsewhere** (`src/lib/currency.ts`, pure and unit-tested; migration 14). The server alone decides the currency of an order, from the buyer's country as the host reports it (`x-vercel-ip-country` on Vercel, `cf-ipcountry` behind Cloudflare; nothing else — a browser language says nothing about where somebody is): the 21 members of the euro area (Bulgaria since 2026-01-01), their territories that use the euro and the states that use it by agreement (Monaco, Andorra, San Marino, the Vatican, Montenegro, Kosovo — confirmed by the owner) pay in euros, every other country in dollars, and an unknown country (a local machine, a masked address) in euros, the shop's own currency. Two admin settings: `price_unit_cents` (euros) and `price_unit_cents_usd` (dollars, factory default 50 cents — confirmed by the owner: $0.50, like the euro price). `px_start_order(…, p_currency)` prices the order with the matching unit price and snapshots the currency and the unit price on the order; any currency but the shop's own and dollars is refused (`px_bad_currency`). The pages, the availability probe and the checkout all use the same rule; the browser sends back the currency it displayed and, if the server now says another (the buyer's connection moved to another country in between), the order is refused with `px_currency_changed` and nothing is charged. Stripe Checkout takes the order's own currency. `TEST_COUNTRY=US` (test mode only) lets a deployed test site pretend to be abroad, to try the dollar price without a VPN. Not done: exchange-rate tracking (the two prices are independent), tax treatment per currency (see the legal checklist), the country detection on hosts other than Vercel and Cloudflare. (`tests/unit/currency.test.ts`, `tests/db/currency.test.ts`, `tests/e2e/currency.spec.ts`.)

**A site-wide simulation, without any end date** (`NEXT_PUBLIC_STORY_PREVIEW=J-40`, `lib/doom/preview.ts`): every visitor sees the story as a `?preview=` simulation (the plate says "FICTION · 100 DAYS" like the real story would — PREVIEW only when a visitor asks for a moment with `?preview=` themselves, `isVisitorPreview`; the clock restarts at each visit), while the real shop is untouched (the server only knows `NEXT_PUBLIC_WORLD_END_AT`, so purchases never close). `?preview=off` switches it off for a tab (remembered in `sessionStorage`), `?preview=default` brings it back; `lib/config-check` warns that it is set and refuses a value that is not a moment of the story. For a test site; a real launch removes it and sets the real date.

**No purchase after zero** (`src/lib/doom/sales.ts`, the owner's decision): once the countdown has reached zero (`NEXT_PUBLIC_WORLD_END_AT`), `POST /api/checkout` refuses to start any order (`403 px_world_ended`; a payment already under way is not touched, the webhook still fulfils it), `getPricing().salesOpen` turns false, and the interface follows the same clock: the header button becomes "Meet the survivors" (a link to Discover), the buy mode cannot be entered (not by the button, nor by `?buy=1` or a resumed purchase link) and a visitor choosing a spot when the countdown reaches zero is taken out of it. The DB-level switch `sales_open` stays the admin's own.

### The home page is the flat map (2D only)

Routes: `/` and `/map` are the same page (`src/app/[locale]/page.tsx` re-exports `map/page.tsx`): the flat map where pixels are bought and drawn (deep links: `?x&y&z`, `?bx&by&bw&bh`, `?p=code`, `?buy=1`). `/globe` only redirects to `/`. There is **no 3D globe**: it was removed on purpose, so zooming out stops at the whole-world floor (the world fits the screen; the map still wraps horizontally) and nothing switches to another page or renderer. No WebGL is used anywhere.

**The parcel card** (`ParcelCard`, on the map and on `/p/<code>`): share, like, **Comment**, report. (There is no "open page" button: the card is the page.) *Comment* opens the parcel's comment area (`Comments.tsx`): the first page is loaded with the card so the button can show the count; writing needs an account (otherwise a sign-in link), a comment can be deleted by its author, the parcel's owner or a moderator (the API tells each viewer whether `canRemove`), and reported by other signed-in users (`/api/reports` with `commentId`; the admin report shows the words and a *Delete the comment* button → admin action `remove_comment`). `/api/comments`: `GET ?code&before` (keyset cursor `created_at|id`, 20 per page, newest first), `POST {code, body}`, `DELETE {id}`.

**The map's left column** (explore mode): a *latest creations* tile (`LatestTile`: the 4 newest published creations of `latestCreations(4)`, public data only — with none yet it says so instead of showing made-up ones; a click flies to the parcel and opens its card, the arrow opens `/discover`; hidden on phones and on screens shorter than 640 px), then the live counter (`StatsCard`: pixels sold / land total, and the progress bar with the real share sold beside it — two significant digits below 1 %, so it never reads "0 %" once something is sold).

The 1:10m layers are **not** loaded as a whole: `public/data/geo/` holds them cut into 2 500-px cells (`g-{cx}-{cy}.json`: land, country borders, admin-1 borders; `c1-…`: cities 15 000–400 000; `c2-…`: towns 1 000–15 000 in 625-px cells), plus `index.json` listing the non-empty cells. The engine fetches a cell when a tile or label layer needs it (6 requests at a time, newest first, LRU-evicted) and draws the 1:50m level meanwhile; tiles are redrawn when the cells arrive. A cell's polygons are cut exactly at its border and their coastline is derived on the client by skipping the edges that merely lie on the border, so there are no false lines and no seams. `scripts/build-world-data.mts` produces everything (`npm run data:world`, ~10 s; needs the 40 MB Natural Earth admin-1 file, downloaded once into `.data/`).

**Why the map is cheap to move.** Borders are *solid* thin lines (dashes cost 3× more to rasterise and read as noise), made discreet by their opacity, and commune borders only exist from ×8 up. Measured in headless Chromium with software rendering, rasterising every tile of a Paris view from scratch: ×2 38 → 15 ms, ×4 65 → 17 ms, ×8 120 → 11 ms, ×16 67 → 20 ms (before → after). On top of that the engine **prepares tiles in advance**: 220 ms after the camera stops it rasterises, one tile per idle slot (`requestIdleCallback`), the ring of tiles around the view, the middle of the view one zoom step closer and the view one step further (`warmNow`, at most 60 tiles in the cache; less on phones with < 4 GB or in data-saver mode), and requests their geometry too, so a pan or a zoom step finds them ready and only blits. Any change on screen cancels the pending preparation. (`tests/e2e/map-perf.spec.ts`.)

**A modest PC (the owner's second computer was "very slow, above all when zooming").** Measured on the production build with the story on and a processor slowed 6× (`Emulation.setCPUThrottlingRate`; `tests` do not cover wall-clock speed, only the mechanisms): a zoom step took 200–300 ms per image, and **half of it was making new tiles in the middle of the movement** (each level change needs a dozen land tiles, a dozen destroyed-sea tiles, and the corruption is painted into each). Two changes, both inert on a fast machine: (1) **a machine that struggles is recognised by its own frames** (one longer than 45 ms marks it slow for 8 s, `slowUntil`); while the camera moves — a zoom or a flight, a drag, inertia, the wheel — and 140 ms after, **it makes no new tile** (`deferBaking`): the coarser ones in memory stand in (a little soft), and the sharp ones are made the moment it stops, a few per frame as before; drawing time at ×6 went from 213 to 118 ms per image, the geography part from 96 to 8 ms. (2) The page (React) used to be re-rendered at every camera change, i.e. at every wheel notch; **it now hears about the camera at most every 120 ms, and always about the last position** (`notifyCamera`). The rest of a frame on that test machine is the browser's own software rendering of the canvas, which a PC with a graphics card does not pay: **add `?hud` to the address** to see, in a corner of the map, the real time per image, images per second, tiles made per second, the screen density and cores of the machine — a screenshot of it from the slow PC tells what is left to do.

**No blue holes while tiles are made.** At most 4 geography tiles are rasterised per frame (the ones nearest the middle of the view first); a tile that is not ready is shown from the nearest coarser tile (at most 3 levels away, each level doubling the width of its lines), else from a soft **fill-only world base** (6 tiles at level −5, pinned in memory, no lines so that nothing is stretched into a band), with any finer tiles already in memory shrunk over it. So zooming out, zooming in fast or jumping to a place never seen shows blurry land and sea for a few frames instead of the ocean colour showing through over land (`tests/e2e/map-perf.spec.ts` samples every frame of a zoom-out and of jumps: 8 of 76 frames flashed before, none now).

Frame cost measured in headless Chromium with *software* rendering (no GPU): ≈ 0.4–2 ms per frame at world and deep zoom, ≈ 9 ms at mid zoom (many large tile blits); real GPU-accelerated browsers are considerably faster. `tests/e2e/ui.spec.ts` guards against regressions.

**Cache invalidation:** `map_state.version` is bumped (once per statement) whenever the visible map changes. Clients learn it
from `/api/stats` (15 s cache) and put it in every tile URL, so tiles are `immutable` and never stale.

**Scale-out path:** raster tiles are rendered on demand and cached by the CDN. If very large volumes make cold tiles slow, move
`renderRasterTile` to a background worker writing to storage (each level is derivable from the level below) — the URL scheme
and the client do not change.

## 3. Data flow of a purchase

```
browser                       Next.js (server)                         PostgreSQL                 Stripe
  │ place + design (local)         │                                       │                        │
  │── GET /api/availability ──────▶│ px_is_area_free (read-only)           │                        │
  │── POST /api/checkout ─────────▶│ validate image (content!)             │                        │
  │                                │── px_start_order ────────────────────▶│ tile locks, exclusion  │
  │                                │   reserved parcel + priced order      │ constraint, hold 35min │
  │                                │── checkout.sessions.create ──────────────────────────────────▶│
  │◀── redirect to Stripe ─────────│                                       │                        │
  │                                                                        │          pay           │
  │                                │◀── POST /api/stripe/webhook (signed) ─────────────────────────│
  │                                │── px_fulfill_order (idempotent) ─────▶│ parcel → active        │
  │── /checkout/success (polls) ──▶│ order status (informative only)       │                        │
  │                                      moderator approves ─▶ px_review_asset ─▶ creation public    │
```

The browser's return from Stripe is **never** proof of payment. The only paths that attribute a parcel are the verified
webhook and the server-side reconciliation (which asks Stripe's API).

### An account is required to buy

Paying needs a signed-in account (`requireActiveViewer` in `POST /api/checkout`; an anonymous visitor who clicks *Sign in to continue* is sent to the sign-in page and brought back to the same spot). The account is what lets an owner manage their parcels afterwards: *My parcels*, editing the creation, the orders, and sharing a drawing link. Suspended accounts cannot buy.

## 3b. Drawing together

The owner of a parcel (in *My parcels → Draw together*) creates a **secret link** `/draw/<token>`. Anybody holding it — no account — paints pixels on that parcel: a streamer lets their community draw, a school class draws one picture, and so on.

* **An overlay, not the creation.** Strokes are stored in `parcel_collab_pixels` (sparse: only painted pixels) on top of the parcel's *approved* creation (white while none is approved). They never appear on the map by themselves. The owner **publishes** the result: the server composes approved creation + overlay into a PNG and submits it as a **new version** (`px_add_asset`), which waits for a moderator like any edit. So everything the map shows is still moderated, whoever held the pen.
* **Live without WebSockets.** The page sends its strokes in small batches (`POST /api/draw/:token/pixels`, ≤ 2 000 pixels) and polls `GET /api/draw/:token?since=N` every 2 s for what changed after version N (a few bytes when nothing did). Painting takes a row lock on `parcel_collab`, so versions are assigned in commit order and "everything after N" can never miss a change. Last write of a pixel wins.
* **The link is the capability** (160-bit random token). The owner can renew it (the old one dies, the drawing is kept), switch it off (the drawing is kept), reset the drawing (connected pages reload it), and publish. A parcel hidden by moderation, revoked, or whose owner is suspended stops accepting strokes at once; unknown, closed and hidden links all answer the same 404.
* **Abuse limits.** Per address: 120 paint requests and 240 reads a minute; per link: 6 000 paint requests a minute; the database refuses anything outside the parcel; owner actions are written to `audit_logs`. The page is `noindex` and sends no referrer, since the URL is a secret.

## 4. Modules

* `lib/grid` — pure geometry/pricing shared by client and server (tested exhaustively).
* `lib/db` — `pg` pool, transactions with deadlock retry. All business writes call `px_*` SQL functions.
* `lib/auth` — Supabase SSR session (production) or a signed dev cookie (development only, impossible in production).
* `lib/stripe` — checkout creation, event handling (idempotency ledger), reconciliation, auto-refund.
* `lib/collab.ts` — drawing together: state/delta reads, validated paint batches, snapshot publishing.
* `lib/images` — content sniffing, decompression-bomb guard, canonical PNG re-encode, average colour, hash.
* `lib/storage` — private object store: Supabase Storage in production, local files in development.
* `lib/rate-limit` — PostgreSQL fixed-window counters shared by all serverless instances.
* `lib/data` — read models (tiles, stats with cache + tag invalidation, parcels, discovery, admin).

## 5. Internationalisation

All user-facing text lives in `src/messages/<locale>.json`; a unit test enforces identical keys and placeholders between
languages. English is the default (served at `/`), French at `/fr`. To add a language: create `src/messages/xx.json`, add
`"xx"` to `src/i18n/routing.ts`. Prices and numbers use `Intl` for the active locale; country names use `Intl.DisplayNames`.

## 6. Public statistics

`px_public_stats()` computes sold pixels, parcels, owners and published creations from real rows (reservations are *not*
counted as sales). The result is cached 15 s (`unstable_cache`, tag `stats`) and invalidated after every payment/admin
action. If the database is unreachable the UI says so rather than showing a number.

## 7. Known limits / next steps

* Raster tiles are generated on demand (see scale-out path above).
* Sitemap is capped at 45 000 parcels per file; switch to `generateSitemaps()` beyond that.
* Email notifications (purchase confirmation, moderation outcome) rely on Stripe receipts / Supabase Auth emails for now.
* Parcel transfer/resale is deliberately out of scope for v1.
