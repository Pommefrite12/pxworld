# Architecture

## 1. The billion pixels

| | |
|---|---|
| Grid | **40 000 × 25 000 = 1 000 000 000** cells (`src/lib/grid/constants.ts`, mirrored by CHECK constraints in SQL) |
| Why not 2:1 | 10⁹ = 2⁹·5⁹, so width/height = 2ᵃ·5ᵇ with *a, b odd*: 8:5 (40 000 × 25 000) or 5:2 (50 000 × 20 000) are the closest to a world map; 8:5 is used |
| Projection | **Web Mercator** (`src/lib/grid/projection.ts`): x linear in longitude, y = `(M(latMax) − M(φ))·Ry` with `M(φ) = asinh(tan φ)`. Conformal: countries keep their familiar shape at every latitude (an equirectangular map looks stretched near the poles). `Ry` fits the latitude band exactly into the 25 000 rows, ≈ 5 % below the horizontal scale `R = W/2π` (a Mercator 5 % flatter than a pure one, invisible). One pixel ≈ 1 002 m wide at the equator, ×cos(latitude) elsewhere |
| Coverage | lat **56.7°S → 83.8°N**: all of Greenland (83.67°N) and Chile's Diego Ramírez islands (56.5°S) fit; only Antarctica is cropped. Longitude **168.5°W → 191.5°E**: the map's edge lies in the Bering Strait, the one meridian that slices no country (only the Aleutian island of Umnak straddles it): Russia is whole at the east edge, Alaska starts at the west edge. **The world wraps horizontally** in the engine: the scene is drawn once per visible copy of the world (`offX = c·W`, used by `worldToScreen`/`visibleWorld`), the camera's x is taken modulo W, `screenToWorld` maps any point of a copy back to its real grid position (so hit-testing, selection and purchases are unaffected), and `flyTo` takes the short way round. On a window wider than the planet the continuation shows at the sides; the world is never closed by a frame on the left or right. Rings that straddle the map's own edge are emitted on both sides by the build script; polygons that the source data cut along the antimeridian (Chukotka, Fiji…) now meet in the middle of the map and their shared edge is never stroked (`outlineWithoutClipEdges(…, seamX)`) |
| Parcel | integer rectangle `(x, y, w, h)`, area ≥ 100, sides ≤ 1000, area ≤ 250 000 by default (admin setting; hard cap 1 000 000) |

The grid is **virtual**. Nothing ever materialises one object per pixel: only purchased rectangles are rows.

## 2. Rendering engine (why a custom Canvas 2D renderer)

The map is a flat 40 000 × 25 000 pixel plane (Mercator-projected geography on top of an integer grid). MapLibre/Leaflet are built
around tile pyramids of that same projection but would need bolt-on code for pixel-exact images and a grid of exactly 10⁹ cells; OpenSeadragon needs a pre-rendered deep-zoom pyramid of
the *whole* planet. A purpose-built engine (`src/components/map/engine.ts`) gives one coordinate system for geography, parcels
and overlays, nearest-neighbour pixel-exact zoom, touch/pinch/inertia, and no tile infrastructure.

Layers, by zoom (`scale` = screen px per grid px, 0.029 … 48):

| Layer | Source | Notes |
|---|---|---|
| Ocean, land, country borders | static vector data (`public/data`, Natural Earth) | rasterised **once per tile** into 512-px offscreen canvases, clipped per tile (Sutherland–Hodgman / Liang–Barsky) so a frame is a few `drawImage` calls. **Three levels of detail** picked from the zoom `k = ⌈log₂(scale·dpr)⌉`: 1:110m (k ≤ −2), 1:50m (k = −1), 1:10m (k ≥ 0) |
| Départements / states / provinces | Natural Earth admin-1 | internal borders only (arcs shared by two units of one country; the country outline comes from the country layer). Coarse simplified file `admin-lo.json` for k = −3…−1, 1:10m cells beyond; thin solid line. In metropolitan France the département borders are derived from the commune data instead, so they coincide exactly with the commune lines |
| Communes (France) | Etalab communes (simplified), via `gregoiredavid/france-geojson` | 35 228 communes → topology (shared arcs) → internal borders between communes of the same département, in 250-px cell files `geo/m-{cx}-{cy}.json` (≈ 40 KB each, 33 files), drawn from zoom k ≥ 4 (≈ ×8, when a commune is ~70 px wide; `COMMUNES_FROM_K`) as fine solid lines — and the chunks are only downloaded then. Other countries: add a source in `scripts/build-world-data.mts` (`chunkCommune` is country-agnostic) |
| Place names | countries, big cities (≥ 400 000, always loaded), admin-1 names (`admin-labels.json`, shown once the unit is wide enough to hold its name), cities 15 000+ (zoom ≥ 1.1×) and towns 1 000+ (zoom ≥ 6×) | greedy collision avoidance, most important first; localised (en/fr) for countries and admin-1; zoomed in, names sit under the parcels; zoomed out (< ×1) they are drawn on top, **except across a parcel at least 24 px wide and high on screen** (`bigParcelBoxes`: such parcels are obstacles in the same collision list, so a big creation is never written over, nor marked with a city dot) |
| 1-px grid | procedural, **land only** | the **only** grid: 1-pixel lines, shown in the last stretch of the zoom only (fading in from ×24 to ×30, the maximum being ×48; `gridAlpha` in `src/lib/map/pixelGrid.ts`). No 10 px / 100 px lines and no dot matrix at any zoom. Clipped to the land path of the current level of detail (`landPath`/`onLand` in the engine, cached while the camera stays inside it), so oceans and seas stay clean — they are not for sale |
| Parcels, scale < 1 | `/api/map/raster/{z}/{x}/{y}?v=` | 256-px PNG tiles composited by `sharp` from parcel images, z = 0…8, **immutable per map version** (CDN). From level 3 on (1/8 pixel or less per grid pixel) a parcel of at most 8 px on the tile is its **average colour**, its picture is not even fetched (`FLAT_FROM_LEVEL`); the pictures fetched are kept in a 48 MB in-memory cache of the server instance (a stored file never changes) |
| Parcels, scale ≥ 1 | `/api/map/tiles/{x}/{y}?v=` (JSON, 1000×1000 px) + `/api/assets/{id}` | only tiles in view; images loaded lazily, drawn with smoothing **off** so pixels stay razor sharp. The tile queue is **not** first-come first-served: a tile not wanted for 2 frames is forgotten, the nearest to the screen centre goes first (8 at once) — zooming from the world to a city crosses ~100 tiles nobody sees, which once left the final view empty for seconds. Until a tile arrives, the coarser rasters already in memory stand in for its parcels (clipped to that tile). Likewise, until the picture of a creation (at least 12 px on screen) has arrived — a big one is a big file — the **raster picture of that very place** is drawn in its rectangle (clipped; only the raster tiles under it are asked for), never a flat block of its average colour (`waiting` in `drawParcelsOf`; `tests/e2e/map-parcels.spec.ts`, with the pictures slowed down) |
| Hit-testing, collisions | the same JSON tiles | client-side convenience only; the database decides |
| Overlays | selection, preview of the buyer's creation, highlight | |

### Price per pixel

The unit of sale is the **pixel** (default **€0.25**, `app_settings.price_unit_cents = 25`, admin-editable; migrations 7, 8 and 16 move the earlier factory defaults of 100, 10 and 50 cents to 25 and leave any other price an admin chose alone, so a site where an admin typed a price on purpose keeps it: read `/admin/settings` to know the real one). The price list is one table, checked at every layer (`tests/unit/price-table.test.ts`, `tests/db/price-025.test.ts`, the buy-panel test in `tests/e2e/ui.spec.ts`): 25 px = €6.25 · 50 px = €12.50 · 100 px = €25 · 200 px = €50 · 400 px = €100, for a parcel entirely on land (a water parcel costs the same at the default rate of 100 %). A parcel's surface is its number of pixels, and so is its price: two parcels of the same size cost the same wherever they are.

### Draw order on the map

Geography → (zoomed in) place names → **1-px grid** (land only, last zoom stretch only) → **parcels** (their drawing cut along the coast) → place names when zoomed out → overlays (selection, highlight). The grid is a guide to *free* land, so it sits under the parcels: a taken parcel shows its creation (or, while it awaits moderation, its neutral block) with no grid line across it (`tests/e2e/map-parcels.spec.ts` checks every pixel of a parcel).

### Drawing finer than a pixel (down to 0.1 px)

The grid does not change: a parcel is `w × h` **pixels**, those are what is sold, counted (`available`, `sold`) and priced (€0.25 each). What changes is how finely a creation is **drawn**: every pixel holds `k × k` dots, so the finest brush is `1/k` of a pixel — **0.1 px** when `k = 10`. The editor offers 0.1, 0.2, 0.5, 1, 2, 3, 5 and 8 px (those that are a whole number of dots at the parcel's precision).

* **Precision is capped by the size of the image**: `k` is the largest value ≤ 10 with `k² · w · h ≤ 4 000 000` dots (`creationScale()` in `src/lib/grid/constants.ts`, `px_dot_scale()` in SQL, tested to agree). A 20 × 20 or 200 × 200 parcel gets the full 10 × 10 dots per pixel; a 500 × 500 parcel (the default maximum area) gets 4 × 4 (0.25 px); a 1 000 × 1 000 one gets 2 × 2.
* A creation image is the parcel's size **times any whole scale from 1 to `k`** (`px_add_asset` and `processCreation` check it; anything else is `px_bad_dimensions`). Older creations (1× or 2×) stay valid. The asset rows keep the real image size.
* **The editor** works in dots, with a zoom (so that a tenth of a pixel is reachable) whose **1× always shows the whole parcel in the space available, whatever its size** (`src/lib/editor/zoom.ts`: the fit is measured from the width and the height, the next levels magnify from it, up to a dot of 48 screen pixels; the same on the shared drawing page), a pan tool, a flood fill on typed arrays and an undo whose memory is bounded (every snapshot is a full copy of the canvas). A very detailed picture that would exceed the upload limit (3 MB) is sent at half the precision, then half again.
* **Colours.** The text layer has **its own colour** (a block of its own in the text panel; it starts in the current stroke colour and is never changed by choosing a stroke colour, nor the other way round). The pencil can be a **multicolour brush** (`Palette.tsx`, shared by the editor and the shared canvas): switch it on, click colours to add or remove them (at most 8, never none; each shows its rank), and the stroke runs through them in order, **one brush width of each** and never less than a whole pixel (`strokeRun`, `mixColor` in `src/lib/editor/colors.ts`, unit-tested). The colour of a dot depends only on how far the stroke has travelled, so fast and slow strokes look the same; the eraser and the fill are unaffected (the fill uses the colour last picked). On the shared canvas every dot of a multicolour stroke is sent with its own colour. (`tests/e2e/editor-colours.spec.ts`, `tests/e2e/together.spec.ts`.)
* **Images are served at the size the screen needs.** `/api/assets/:id?max=N` (N in 64, 128, 256, 512, 1024, 2048) returns the creation shrunk (area-averaged, never enlarged) so that its longest side is at most N. The map engine asks for the size a parcel occupies on screen (and shows a smaller variant already in memory meanwhile), cards and thumbnails ask for theirs; the moderation queue and the editor load the original.
* The map shows dots crisply once they are magnified (≥ 1 dot per device pixel); a finer creation drawn smaller is averaged (canvas smoothing in the engine, lanczos in the server's raster tiles and OG images).
* "Draw together" works in dots too: its overlay is `k·w × k·h`, and a published snapshot is composed at that resolution (an older creation underneath is enlarged by nearest-neighbour, so nothing is invented). Migrations 10 and 11 convert overlays drawn at the previous precisions.

### Land and water are for sale — two categories, each pays for what it owns (migration 15)

A parcel is a rectangle with a **kind**: `land` (every parcel so far) or `water`. A **land** parcel owns the *land* pixels of its rectangle; a **water** parcel owns the *water* pixels of its rectangle. The other pixels are **cut away**: they are not the parcel's, they are not shown as its, and they are free (or discounted). Land and water never share a pixel, so a land parcel and a water parcel may sit on the very same rectangle. Admin settings (`app_settings`, editable in the back office):
* `min_land_percent` (default **50**): at least this share of a land parcel's pixels must be land (1–100).
* `sea_price_percent` (default **0**): a sea pixel cut away from a land parcel costs this % of a land pixel (0 = offered; 0–100).
* `min_water_percent` (default **50**): at least this share of a water parcel's pixels must be water (1–100).
* `water_price_percent` (default **100**): an owned water pixel costs this % of a land pixel (1–1000; 100 = same price).
* `land_cut_price_percent` (default **0**): a land pixel cut away from a water parcel costs this % of a land pixel (0 = offered; 0–100).

Price of a land parcel = `land × unit + ⌊sea × unit × sea% / 100⌋`; of a water parcel = `⌊water × unit × water% / 100⌋ + ⌊land × unit × cut% / 100⌋` (`quote()` in `src/lib/grid/pricing.ts`, the same integer arithmetic as `px_start_order`; the order stores `kind`, `land_px`, `sea_percent` (the percentage of the cut-away pixels, whichever kind) and `water_percent`, and `orders_amount_consistent` keeps the amount explainable from the row alone). The buy panel and the order summary show the split ("1 486 px of your parcel are sea, offered: you only pay for the 2 114 px of land"; for water: "…are land, offered: you only pay for the … px of water").

**Whatever a buyer creates on water is shown in three blues.** Customisation, moderation and payment are the same for both kinds; only the DISPLAY differs. `src/lib/images/waterTint.ts` (pure, unit-tested; palette light `#7fc8f0`, medium `#2f8fd8`, deep `#1b4f9c`, chosen by lightness) turns any picture into those three tints. The stored original never changes: `/api/assets/:id` serves the blue version to the public (tinted first, shrunk after), and the original to the uploader and the staff with `?raw=1` (the editor and the moderation queue ask for it); the server raster tiles, the metadata tiles' average colours, and the buyer's preview on the map (`tintedBlob`, `MapEngine.shownPreview`) use the same tints. **On the map, a water parcel is drawn a little see-through** (`WATER_ALPHA = 0.62` in `engine.ts`, applied to the whole water pass — the water raster layer and the per-parcel drawing alike, so nothing jumps when the zoom changes from one to the other): the sea shows through and the opaque cream of the land stands out against it. The parcel's own page, the cards and the thumbnails keep the full blues. (`tests/e2e/map-water.spec.ts` checks the pixel is the blue blended with what is under it, not the raw blue.)

**Display latency (measured on the production build, network 120 ms and processor ×4 slower; before → after):** the world view asked for 176 requests and now asks for 62 (the water layer is only asked for where `/api/map/water` says there is a water parcel; the raster level follows the DEVICE pixel, one level coarser on an ordinary screen, four times fewer tiles), and a zoom to Europe went from 320 requests to 100; the map was complete after 6.3 s and now after 3.9 s (8.5 s → 5.4–6.2 s with the story). Tiles of land and sea are made on a time budget per frame (`BAKE_BUDGET_MS`, at least one per layer), arrivals share a redraw (`invalidateSoon`, 60 ms), and the destroyed-sea tiles are prepared with the others while the map is idle. `?perf` in the address exposes the engine in production (`window.__pxEngine`) to measure the real build.

**Display latency, second pass (November 2026, with the 100 "heritage" demo parcels; same method: production build, network 120 ms and 10 Mbit/s, processor ×4 slower, three runs each, old and new engine side by side).** Three changes, all about asking sooner and asking less: (1) **the page that opens on the whole planisphere preloads its pictures** (`app/[locale]/map/page.tsx`: the 20 raster tiles of level 5, with the map version in the address, `media="(min-width: 1024px)"` so that phones, which show the world at a finer level, do not download them; none for a deep link to a place): the first raster request now leaves 0.2 s after the navigation instead of 1.2 s (after the scripts have run), and the last one arrives about 0.7 s earlier; (2) **a flight (search, "see it on the map", a zoom) asks for its destination at once** (`MapEngine.prefetchDestination`, each frame of the flight: the metadata tiles of the view it ends on and, as soon as they are here, the pictures of the parcels in it, at the size that view needs), instead of two network round trips after it has landed; (3) **the levels a flight only passes through are asked for only where the camera is heading** (`destinationView`, in `drawRasters`; the other tiles are drawn from what is in memory): raster requests during a flight from the world to Paris went from about 42 to 20. Result: a deep zoom onto parcels is complete after 1.05 s instead of 1.27 s (−17 %), a zoom to Europe after 2.4–2.7 s instead of 2.7–2.8 s, and the server is called about half as often for rasters. What is NOT slow: the engine's own JavaScript (a profile of a zoom and a pan shows a few hundred milliseconds of script in several seconds of browser work), and the server per request (a cold raster tile takes 5–110 ms locally). What the owner sees on the deployed site also depends on what a locally measured build cannot show: Vercel cold starts and the round trips to Supabase for the first visitor after a map change (every tile URL carries the map version, so a change makes the next visit start from cold caches; the CDN then serves everybody from the cache). Tests: `ui.spec.ts` (the preload links; the flight asks only for the destination's level or the tiles on the way, which fails on the old engine).

**One guarantee per kind.** `parcels_no_overlap` became two partial exclusion constraints, `parcels_no_overlap_land` and `parcels_no_overlap_water`; `px_is_area_free(…, kind)` and `px_start_order(…, kind)` take the kind (last, optional argument: every older call is a land purchase). `parcels.owned_px` (generated) is what a parcel really owns, whatever its kind.

**The destroyed sea is a plain lavender field** (scanlines only): the error colours (magenta, cyan, orange…), the sliding bands and the colour fringe along the edge of a destroyed area belong to the LAND alone. **While buying water the colours are swapped** (the water is cream, the land takes the colour of the sea); in both modes it is the water that is hatched, so that nobody mistakes one for the other.

**On the map**, water is drawn **under the land**: ocean colour → water parcels → land tiles (opaque on land, so the coast cuts every water parcel exactly, at every zoom, with no clipping) → land parcels (clipped to the land as before). The server's raster tiles have two layers (`/api/map/raster/{z}/{x}/{y}?v=` for land, `&k=w` for water). Hit-testing asks who OWNS the pixel under a point (`MapEngine.parcelAt` + `landAt`): the land parcel on land, the water parcel on water, so the cut-away part of a parcel is not clickable. While buying, the selection only collides with parcels of its own kind (`setBuyKind`), and the colours are swapped when buying water.

*Land* means: the pixel's centre is inside the Natural Earth 1:10m land polygons (even-odd) — the same data files the map draws (`public/data/geo/g-*.json`). `src/lib/geo/landmask.ts` scan-converts the polygons for just the window being asked about (no bitmap, no table of cells: a 20×20 parcel is one pass over the edges of ≤ 4 cells, a 1 000×1 000 one is still instant).
* **Server (authoritative):** `landServer.ts` counts the land pixels in `POST /api/checkout` *before* any pixel is held (→ 422 `px_not_on_land` below the minimum share) and passes the count to `px_start_order(…, p_land)`; the availability probe returns `landPixels`, `onLand` and the quote. PostgreSQL range-checks the count (1 ≤ land ≤ area, share ≥ `min_land_percent`), computes the price from `app_settings`, stores `land_px` and `sea_percent` on the order and `land_px` on the parcel, and the `orders_amount_consistent` constraint keeps the amount explainable from the row alone. The cells are cached in memory (24, LRU) and `outputFileTracingIncludes` ships the data files with the serverless functions. The land count itself is trusted from the app server (PostgreSQL has no map); `px_*` functions are not callable by browsers, so the HTTP routes are the only way in.
* **Browser (courtesy):** `Geo.landIn` gives the buy panel an instant answer (`water` state below the minimum share, red selection and dashed ghost, live price); while buying, the sea is hatched under the land tiles.
* **Counters:** `px_public_stats()` sums `owned_px` — every pixel owned, land and water — against `TOTAL_PIXELS` (the whole 40 000 × 25 000 = 10⁹ grid): *sold / planet*, *available = planet − sold*, with the water share on its own (`water_pixels`, `water_parcels`). The 308 046 591 land pixels (30.8 %, `npm run data:world` → `src/lib/geo/landPixels.ts`) are only used to price and count the cut.
* **The drawing is cut along the coast.** The parcel stays a rectangle (that is what is chosen, bought and priced), but on the map only the part of its drawing that lies on its own kind of pixels is shown: the engine clips land parcels (and the editor's "Preview on the map") with the same land path as the grid, so the sea stays sea; water parcels are cut by the opaque land drawn over them. The parcel's own page, card and share image show the whole drawing. Covered by `tests/e2e/map-parcels.spec.ts` (a coastal parcel shows its drawing on ≈ 53 % of its rectangle, the land share, and the sea elsewhere).
* Parcels bought before the rule existed have `land_px = NULL` (= all land) and are untouched.
* Lakes: only what the 1:10m land layer cuts out is water (the Caspian); ordinary lakes (Victoria, Baikal, the Great Lakes…) are land in this data. Adding Natural Earth's lakes layer would change that.

### The old countdown story: removed (step D6)

The site used to carry a story laid over it, "365 days to save the world" (Protocol ZERO, art direction Glitch): a countdown to the fictional destruction of the digital world, corrupted land on the map, a bug every 30 s, a final sequence, a picture book, a share image that followed it. **All of it has been removed** (`PLAN_REFONTE_ARCHIVE.md`, D6) — components, pure modules, pictures, the corruption and the final sequence in the map engine, the second (light) palette of the map, the `doom.*` and `comic.*` texts, the styles, and the variables `NEXT_PUBLIC_WORLD_END_AT` and `NEXT_PUBLIC_STORY_PREVIEW`. Git keeps the old code. What remains of it: a warning of the configuration check (`config-check.ts`) if one of the two variables is still set in an environment ("no longer used: remove it"); `/?preview=…` is now just the home page. **Buying, parcels, accounts, moderation and the map were never touched by it.**

**The share image** (`src/app/api/og/home/route.tsx`) is now a single picture in the night palette, in the language asked (`?lang=fr`, otherwise English): the logo, "COLLECTIVE ARCHIVE", the sentence of the home page, a row of lit pixels. It is the same for everybody and keeps for a day; every page of the site announces it unless it has an image of its own (`/api/og/parcel/<code>`). Set in the pixel font (the file is carried into the serverless function by `outputFileTracingIncludes`).

**Two currencies: euros in the euro area, dollars elsewhere** (`src/lib/currency.ts`, pure and unit-tested; migration 14). The server alone decides the currency of an order, from the buyer's country as the host reports it (`x-vercel-ip-country` on Vercel, `cf-ipcountry` behind Cloudflare; nothing else — a browser language says nothing about where somebody is): the 21 members of the euro area (Bulgaria since 2026-01-01), their territories that use the euro and the states that use it by agreement (Monaco, Andorra, San Marino, the Vatican, Montenegro, Kosovo — confirmed by the owner) pay in euros, every other country in dollars, and an unknown country (a local machine, a masked address) in euros, the shop's own currency. Two admin settings: `price_unit_cents` (euros) and `price_unit_cents_usd` (dollars, factory default 25 cents — $0.25, like the euro price: the owner moved both from 50 cents with migration 16). `px_start_order(…, p_currency)` prices the order with the matching unit price and snapshots the currency and the unit price on the order; any currency but the shop's own and dollars is refused (`px_bad_currency`). The pages, the availability probe and the checkout all use the same rule; the browser sends back the currency it displayed and, if the server now says another (the buyer's connection moved to another country in between), the order is refused with `px_currency_changed` and nothing is charged. Stripe Checkout takes the order's own currency. `TEST_COUNTRY=US` (test mode only) lets a deployed test site pretend to be abroad, to try the dollar price without a VPN. Not done: exchange-rate tracking (the two prices are independent), tax treatment per currency (see the legal checklist), the country detection on hosts other than Vercel and Cloudflare. (`tests/unit/currency.test.ts`, `tests/db/currency.test.ts`, `tests/e2e/currency.spec.ts`.)

**Nothing can be bought outside an open edition (migration 19, section 3f below).** Whether anything can be bought is decided by the database (the edition's state, computed from its own clock), never by an environment variable or by the browser.

### Demonstration data for a test site (never for a real launch)

`npm run demo:seed | demo:status | demo:clear` (`scripts/seed-demo.mts`) fills a TEST site with 50 marked accounts (`demo-001@demo.invalid`, username `demo_<word>`, bio "demonstration account") and one parcel each, so that the map is not empty.
`lib/demo/plan.ts` is the plan (deterministic from a seed: anchor city, size 60–400 px, style, title) and the **guards** (`demoGuard`): refuses without `--i-know-this-is-a-test-site`, with a live/restricted-live Stripe key, with `PAYMENTS_LIVE_ENABLED`,
with any `livemode=true` event in the database, and — in Supabase mode — without `--project <id>` matching `NEXT_PUBLIC_SUPABASE_URL` (a database that is not on this machine is refused when no project is configured to check it against). The script applies them before touching anything.
`lib/demo/art.ts` generates the pictures (pure, deterministic RGB rasters: invaders, plasma, emblems, stripes, mosaic, landscapes, icons, words; 5×7 pixel font); `lib/demo/seed.ts` orchestrates through `DemoPorts` (database, account creation, files, land count) so that the tests run it on a scratch database
(`tests/db/demo.test.ts`) and the script on the real one. Parcels are placed around big cities on **land** (≥ 85 % land pixels, counted by the same function as purchases) — every fifth one on the **sea** instead (a water parcel, ≥ 85 % water) — clear of every existing parcel; pictures go through `processCreation` like real uploads.
It creates **no order, payment or moderation action** (no fake revenue or audit trail) and is idempotent; `clear` deletes only `demo-%@<domain>` accounts with their parcels, creations and files. The public counters show these numbers while they exist: **`demo:clear` before the real launch**.

### The home page, and the flat map (2D only)

Routes: **`/` is the home page** (`src/app/[locale]/page.tsx` → `components/home/Home.tsx`, a server component) and **`/map` is the flat map** where pixels are bought and drawn (deep links: `?x&y&z`, `?bx&by&bw&bh`, `?p=code`, `?buy=1`). Every address that was shared as `/?x=…`, `/?p=…`, `/?buy=1`, `/?bx=…`, `/?preview=…`, `/?hud`… was a link to the map and still opens it: `lib/home.ts` lists those parameters (`MAP_PARAMS`, `opensTheMap`), and the page renders the map for them. `/globe` only redirects. There is **no 3D globe**: it was removed on purpose, so zooming out stops at the whole-world floor (the world fits the screen; the map still wraps horizontally) and nothing switches to another page or renderer. No WebGL is used anywhere. **Arrival on the map never moves the camera by itself** (owner's rule, November 2026): `/map`, `/map?buy=1` (the *Leave my trace* button) and the *Find your spot* button open on the WHOLE planisphere (`fitWorld`); only a deep link that names a place (`?x&y&z`, `?bx&by&bw&bh`, `?p=`) or a click of the visitor's own zooms. In buy mode, while the map is seen whole (`cam.scale < BUY_PLACE_FROM`, 0.3, exported by `engine.ts`) a parcel is a dot of a few screen pixels, so the first click or tap flies towards the place clicked (`MapEngine.click`) and the next one puts the rectangle; the buy panel (`farView` prop) shrinks on a phone to its title and one sentence (`status.placeFar`) while nothing is chosen, so that the planisphere stays visible. The 1:10m layers are **not** loaded as a whole: `public/data/geo/` holds them cut into 2 500-px cells (`g-{cx}-{cy}.json`: land, country borders, admin-1 borders; `c1-…`: cities 15 000–400 000; `c2-…`: towns 1 000–15 000 in 625-px cells), plus `index.json` listing the non-empty cells. The engine fetches a cell when a tile or label layer needs it (6 requests at a time, newest first, LRU-evicted) and draws the 1:50m level meanwhile; tiles are redrawn when the cells arrive. A cell's polygons are cut exactly at its border and their coastline is derived on the client by skipping the edges that merely lie on the border, so there are no false lines and no seams. `scripts/build-world-data.mts` produces everything (`npm run data:world`, ~10 s; needs the 40 MB Natural Earth admin-1 file, downloaded once into `.data/`).

**Why the map is cheap to move.** Borders are *solid* thin lines (dashes cost 3× more to rasterise and read as noise), made discreet by their opacity, and commune borders only exist from ×8 up. Measured in headless Chromium with software rendering, rasterising every tile of a Paris view from scratch: ×2 38 → 15 ms, ×4 65 → 17 ms, ×8 120 → 11 ms, ×16 67 → 20 ms (before → after). On top of that the engine **prepares tiles in advance**: 220 ms after the camera stops it rasterises, one tile per idle slot (`requestIdleCallback`), the ring of tiles around the view, the middle of the view one zoom step closer and the view one step further (`warmNow`, at most 60 tiles in the cache; less on phones with < 4 GB or in data-saver mode), and requests their geometry too, so a pan or a zoom step finds them ready and only blits. Any change on screen cancels the pending preparation. (`tests/e2e/map-perf.spec.ts`.)

**A modest PC (the owner's second computer was "very slow, above all when zooming").** Measured on the production build (with the old countdown story on, since removed) and a processor slowed 6× (`Emulation.setCPUThrottlingRate`; `tests` do not cover wall-clock speed, only the mechanisms): a zoom step took 200–300 ms per image, and **half of it was making new tiles in the middle of the movement** (each level change needs a dozen land tiles, a dozen destroyed-sea tiles, and the corruption is painted into each). Two changes, both inert on a fast machine: (1) **a machine that struggles is recognised by its own frames** (one longer than 45 ms marks it slow for 8 s, `slowUntil`); while the camera moves — a zoom or a flight, a drag, inertia, the wheel — and 140 ms after, **it makes no new tile** (`deferBaking`): the coarser ones in memory stand in (a little soft), and the sharp ones are made the moment it stops, a few per frame as before; drawing time at ×6 went from 213 to 118 ms per image, the geography part from 96 to 8 ms. (2) The page (React) used to be re-rendered at every camera change, i.e. at every wheel notch; **it now hears about the camera at most every 120 ms, and always about the last position** (`notifyCamera`). The rest of a frame on that test machine is the browser's own software rendering of the canvas, which a PC with a graphics card does not pay: **add `?hud` to the address** to see, in a corner of the map, the real time per image, images per second, tiles made per second, the screen density and cores of the machine — a screenshot of it from the slow PC tells what is left to do.

**No blue holes while tiles are made.** At most 4 geography tiles are rasterised per frame (the ones nearest the middle of the view first); a tile that is not ready is shown from the nearest coarser tile (at most 3 levels away, each level doubling the width of its lines), else from a soft **fill-only world base** (6 tiles at level −5, pinned in memory, no lines so that nothing is stretched into a band), with any finer tiles already in memory shrunk over it. So zooming out, zooming in fast or jumping to a place never seen shows blurry land and sea for a few frames instead of the ocean colour showing through over land (`tests/e2e/map-perf.spec.ts` samples every frame of a zoom-out and of jumps: 8 of 76 frames flashed before, none now).

Frame cost measured in headless Chromium with *software* rendering (no GPU): ≈ 0.4–2 ms per frame at world and deep zoom, ≈ 9 ms at mid zoom (many large tile blits); real GPU-accelerated browsers are considerably faster. `tests/e2e/ui.spec.ts` guards against regressions.

**Cache invalidation:** `map_state.version` is bumped (once per statement) whenever the visible map changes. Clients learn it
from `/api/stats` (15 s cache) and put it in every tile URL, so tiles are `immutable` and never stale.

**Scale-out path:** raster tiles are rendered on demand and cached by the CDN. If very large volumes make cold tiles slow, move
`renderRasterTile` to a background worker writing to storage (each level is derivable from the level below) — the URL scheme
and the client do not change.

The browser's return from Stripe is **never** proof of payment. The only paths that attribute a parcel are the verified
webhook and the server-side reconciliation (which asks Stripe's API).

### An account is required to buy

Paying needs a signed-in account (`requireActiveViewer` in `POST /api/checkout`; an anonymous visitor who clicks *Sign in to continue* is sent to the sign-in page and brought back to the same spot). The account is what lets an owner manage their parcels afterwards: *My parcels*, editing the creation, the orders, and sharing a drawing link. Suspended accounts cannot buy.

## 3b. Drawing together

The owner of a parcel (in *My parcels → Draw together*) creates a **secret link** `/draw/<token>`. Anybody holding it — no account — paints pixels on that parcel: a streamer lets their community draw, a school class draws one picture, and so on.

* **An overlay, not the creation.** Strokes are stored in `parcel_collab_pixels` (sparse: only painted pixels) on top of the parcel's *approved* creation (white while none is approved). They never appear on the map by themselves. The owner **publishes** the result: the server composes approved creation + overlay into a PNG and submits it as a **new version** (`px_add_asset`), which waits for a moderator like any edit. So everything the map shows is still moderated, whoever held the pen.
* **Live without WebSockets.** The page sends its strokes in small batches (`POST /api/draw/:token/pixels`, ≤ 2 000 pixels) and polls `GET /api/draw/:token?since=N` every 2 s for what changed after version N (a few bytes when nothing did). Painting takes a row lock on `parcel_collab`, so versions are assigned in commit order and "everything after N" can never miss a change. Last write of a pixel wins.
* **The link is the capability** (160-bit random token). The owner can renew it (the old one dies, the drawing is kept), switch it off (the drawing is kept), reset the drawing (connected pages reload it), and publish. A parcel hidden by moderation, revoked, or whose owner is suspended stops accepting strokes at once; unknown, closed and hidden links all answer the same 404.
* **Abuse limits.** Per address: 120 paint requests and 240 reads a minute; per link: 6 000 paint requests a minute; the database refuses anything outside the parcel; owner actions are written to `audit_logs`. The page is `noindex` and sends no referrer, since the URL is a secret.

## 3e. The search box (places)

Offline, no search service. **Always loaded when the box opens**: the countries, the départements / states / provinces (`admin-labels.json`), the cities of 15 000+ inhabitants (`search-cities.json`) and the biggest ones (`places.json`), plus `x, y`, `lat, lon` and parcel codes. **From three letters on**, two more files come (once, kept for the session): **`search-communes.json`** — every commune of metropolitan France (~35 000, with its département: "Ceyzérieu · Commune · Ain (01)"; built from the Etalab commune outlines already used for the borders) — and **`search-places.json`** — the small places of the world, 5 000 to 15 000 inhabitants, and the French overseas ones from 1 000 (GeoNames); about 0.75 MB compressed together, nothing for somebody who types less. Built by `npx tsx scripts/build-search-data.mts` (the output is committed). The matching (`lib/geo/placeSearch.ts`, pure, unit-tested) ignores accents, capitals, hyphens, apostrophes and dots (`Saint-Jean-de-Luz` = `saint jean de luz`), ranks the exact name first, then names that start with the query, then the bigger place; a commune that is already listed as a city (same name within 30 px) is not listed twice. Cost: 65 ms to index once, about 2 ms per keystroke. Not found: the 37 communes of the Etalab file that have no outline, hamlets, and abroad the places under 5 000 inhabitants.

## 3d. The ranking by likes

**The Discover page** (`/discover`) has four lists, all public data only (a validated, not hidden creation of a visible author): the latest traces, the biggest parcels, the most liked this month, and **the most commented** (`mostCommented`: the number of *visible* comments received; the comments of the parcel's own owner, the removed ones and those of suspended or deleted accounts do not count; ties: the latest comment). The "editorial selection" and the "top contributors" lists were removed at the owner's request (November 2026): the `parcel_features` table and the admin's *feature* button remain, with no public effect for now. `tests/e2e/parcel-most-commented.spec.ts` covers it.

`/ranking` (`/fr/ranking`; linked from the footer and from Discover) ranks the **creations** and the **creators** by the number of likes they received, over **all time, this month (30 days) or this week (7 days)** (`?board=creations|creators&period=all|month|week`, anything else falls back to the defaults). The SQL is in `lib/ranking.ts` (no server-only import) so that `tests/db/ranking.test.ts` runs exactly what the page runs. Rules, so that the ranking stays honest:

* **The owner's own like does not count** (liking one's own creation is still allowed, it is just ignored), nor a like from an account that is **suspended or deleted**.
* Only what the public can see is ranked: an active parcel, **not hidden by moderation**, with a published creation, whose owner is active. A creation with only its owner's like is not ranked.
* **Ties share a rank** (1, 2, 2, 4); inside a rank the earlier published comes first. Only the first 50 are shown.
* A creator's score is the **sum of the likes of all their visible creations**; their best one is shown next to them.

It reads `parcel_likes` (already indexed by parcel and date). At a very large number of likes a materialised view or a cached result would be the next step (not needed now). The page is dynamic (it depends on the query string) and never breaks on a query error (an empty list is shown).

## 3f. The edition (the 365 days) — decided by the database (migration 19)

The 365 days are an **edition** (`editions`, one row: the founding edition). Three recorded states, `prelaunch` → `open` → `closed`; the dates stay **empty** until an administrator opens it, so **the 365 days never start by themselves** (not by a deployment, a setting, an environment variable or a test). A unique index allows ONE edition for now: nothing can create a second one; that is a decision and a future migration.

* **The state is computed from the clock at every call** (`px_edition_state()`, `clock_timestamp()`): from `closes_at` on, nothing can be bought, reserved or started, **even if the scheduled job never runs**. `px_assert_edition_open()` is the first line of `px_start_order`, `px_create_campaign`, `px_start_contribution`, and of the *approval* in `px_review_campaign` (a rejection stays possible). The web application refuses first, with the right reason (`assertSalesOpen`: `px_edition_not_open` 503 in pre-launch, `px_edition_closed` 403 after the closing, `px_sales_closed` for the manual switch), but the database is the judge: a route that forgot would still be refused.
* **A delay for the payments under way** (the reservation time, 35 min by default): a payment started before the closing may finish, and its buyer may still send the creation, during that delay. After it (`px_edition_is_frozen()`), `px_fulfill_order` refunds instead of activating the parcel (`refund_required`, audit reason `edition_closed`), `px_fulfill_contribution` refunds, and the **creations are frozen**: `px_add_asset` (every edit is a new version), `px_collab_paint/reset/enable` (the drawing link can still be switched OFF), `px_comment_add`, and likes (a trigger: users write their likes directly through row-level security; only the user's own INSERT/DELETE is refused, a cascade from deleting an account goes through). Moderation is not a participant: approving a late review, hiding and removing stay possible.
* **The closing job** (`px_edition_sweep()`, run by `/api/cron/maintenance`, by `/api/edition` and by the back office page when they notice the date passed; idempotent, one row lock): at the closing it ends the open group projects (expired, every paid contribution flagged for a refund, the zone released) and rejects the ones nobody reviewed; once the delay (+ 1 minute) is over it takes the **snapshot** and records `closed`.
* **The snapshot** (`edition_snapshots`, append-only like the audit log): a manifest of what the public could see (active, visible parcels of visible owners, each with its approved creation: asset id, version, sha256, path, size, title, description), ordered by code, with the sha256 of the manifest text. Never rewritten: a retraction after the closing, or a creation approved late, is a **new revision** (`px_edition_take_snapshot`, administrators). This is the base of the export and the integrity check (step D8).
* **What an administrator can do** (`/admin/edition`, `POST /api/admin/action`, all `px_edition_*`, role checked again in SQL, **all audited**): open (type the name of the edition; `opens_at` = now, `closes_at` = +`duration_days`); postpone the closing (**only later**, never beyond **twice the length of the edition** after the opening — 730 days for 365, since migration 22; only while open, with a note); close the sales now (type the name); go back to pre-launch (type the name) **only for a rehearsal**: refused as soon as a parcel is reserved or active or any order or contribution was paid; take a new snapshot after the closing.
* **Public read**: `GET /api/edition` → `{ name, state, frozen, opensAt, closesAt, closedAt, serverNow }`, never cached. `serverNow` is the database's clock: a browser counts down from it, never from its own clock, and never decides anything.
* Every parcel has an `edition_id` (a trigger fills it; existing rows were back-filled), which prepares future editions without creating one.
* **Development and tests**: a fresh database is in pre-launch. `npm run dev` (`scripts/dev-migrate.mjs`) opens the edition on the **local** development database only (never a remote one; `PIXELWORLD_DEV_PRELAUNCH=1` keeps pre-launch), the e2e server opens its own isolated database, and the database tests call `openEdition()` (`resetData()` does). On the owner's test site, after applying migration 19: sign in as an administrator, open `/admin/edition`, type the name, click.
* Tests: `tests/db/editions.test.ts` (27: pre-launch, the clock without any job, the delay and the refund, the freeze of every kind of edit, the snapshot and its idempotence under six simultaneous jobs, projects ending with a refund, every administrator tool, the structure, the rights of the browser roles, and a purchase racing the closing), `tests/unit/edition.test.ts`, `tests/e2e/edition.spec.ts`.
* Rollback: the header of `supabase/migrations/20261029000019_editions.sql` lists it; nothing of the shop's money or parcels is touched by migration 19.

## 3g. The archive fields and the page of a trace (migration 20)

Every creation carries, besides its title and its **short description (both required: 3 characters at least, `isValidTitle` / `isValidDescription` in `lib/security/text.ts`, `title_required` / `description_required` from `parseCreationMeta`; owner's rule, November 2026)**, **a category** (a closed list of eleven: arts, daily, family, nature, science, sport, food, tribute, humor, future, other — `src/lib/archive.ts`, repeated as a check constraint, and a test keeps the two lists identical) and, in the database and the API, **the place it is about** (a text of 1–80 characters and an optional ISO country) — **the forms no longer ask for the place and the country** (owner's choice, November 2026: the "For the archive" part of the form is the category only; the value still carries them unchanged, so that a creation that has them keeps them when it is edited, and the API still accepts them). The place is **never a coordinate**: a precise position would be personal data and the archive does not need it (a test checks that no latitude/longitude column exists). It is distinct from where the parcel sits on the map. All three are optional in the database and in the API (a creation made before has none, and the existing API clients keep working); the **interface asks for the category** (the pay button, the "send to moderation" button and the edit button stay off without one). The **archive date** is the day the payment was confirmed (`parcels.activated_at`): no column, nobody can edit it.

* **Written together with the creation**: `storeCreation` runs `px_add_asset` and `px_set_asset_archive` in ONE statement (the new version and its fields exist together or not at all). `px_set_asset_archive` is for the author, on a version still waiting for moderation, refused once the edition is frozen; a group project gets the same through `px_set_campaign_archive` while it is pending, and `px_review_campaign` copies the fields onto the creation when it approves. The community drawing keeps the category and the place of the creation it replaces.
* **Shown**: the map's card (category, place, a link to the archive page), the moderation queue and the projects queue (so a moderator sees what is being archived), the public JSON (`/api/parcels/<code>`: `creation.category/placeLabel/placeCountry`, `edition`), and the page below.
* **`/archive/<code>`** (`src/app/[locale]/archive/[code]/page.tsx`): the page of ONE trace, readable without the map: title, author, "Archived on <date>", category, place, edition ("Founding edition"), the creation at an integer scale (crisp), the description, a share button (the device's own share sheet, otherwise the link is copied), "See it on the map". Indexable once there is an approved creation; before that it says the trace will be public once a moderator has validated it (and is not indexed); a hidden trace shows nothing of its creation. Its metadata carries the canonical address and the share image. The sitemap lists these pages. **`/p/<code>` stays what it was** (the map opened on the parcel, with its card and its comments): it is the address of the place, the archive page is the address of the story.
* The purchase confirmation says "Your trace is now part of the collective archive of our era." and leads to the archive page.
* Tests: `tests/db/archive-fields.test.ts` (8), `tests/unit/archive.test.ts` (7), `tests/e2e/the-archive.spec.ts` (9), and the purchase journey and the group-project flow choose a category.

## 3i. Preserving the archive: the snapshot, the export, the check (migration 21)

* **The snapshot** (migration 19, completed by 21): at the closing the database stores the **manifest** — a JSON array, one item per parcel the public can see, ordered by code, each with its picture's `content_hash` (the sha256 of the canonical PNG), its `storage_path`, title, description, author, archive date, and (since 21) category, place and country — and its hash, `sha256(manifest::text)`. The manifest is built by `px_edition_manifest()` (read-only, not callable by the browser roles) and stored by `px_edition_build_snapshot`; snapshots are append-only (a retraction after the closing makes a new revision by an administrator, `/admin/edition`).
* **The export** (`src/lib/preservation/`, pure and tested; `scripts/export-archive.mts`, `npm run archive:export`): reads a snapshot, fetches every picture from the storage, checks it against the hash in the manifest, and writes a folder (and, with `--zip`, a plain stored ZIP made by a 120-line writer with no dependency, `zip.ts`): `index.html`, `creations/<code>.png`, `manifest.json` (**the exact text the hash was taken of** — `sha256sum manifest.json` gives the recorded hash, so anybody can check it without us), `manifest.sha256`, `manifest.csv` (no formula injection: texts starting with `= + - @` get an apostrophe), `edition.json`, `retractions.json`, `terms/`, `README.txt` (EN/FR) and `SHA256SUMS`. It **refuses** to write anything when a picture is missing or differs (or when the manifest no longer matches the hash stored with it); `--keep-going` writes the gaps down instead. `--preview` is a rehearsal from the live tables (`px_edition_manifest()`), marked PREVIEW in every file.
* **The check** (`scripts/verify-archive.mts`, `npm run archive:verify`): `--dir`/`--zip` checks an export with nothing but itself (SHA256SUMS, the manifest against `manifest.sha256`, each picture against the manifest, the count); with no argument it checks the **live site** — every stored picture against the snapshot — which is what proves a restore or a bucket copy. Exit code 0 or 1, so a script (or a cron) can use it.
* **Why open formats and no importer:** PNG, JSON, CSV, HTML, text. The export must stay readable and checkable in fifty years with a browser and `sha256sum`; it is not re-imported into a database (accounts, orders and payments must not travel with an archive). Restoring a running site is the dump + bucket procedure of `BACKUP_RESTORE.md`, followed by `archive:verify`.
* Tests: `tests/unit/preservation.test.ts` (33: manifest, CSV, checksums against the real `sha256sum`, retractions, the page and its escaping, the ZIP against `python3 zipfile`, export, tampering, verification), `tests/db/archive-export.test.ts` (8: the manifest function, the snapshot, a full export from a real database to a real folder, a swapped picture, a retraction after the closing, the rehearsal).

## 3j. Free imprints (migration 23) — a gift that a purchase covers

At the start of the edition anybody with a **verified e-mail** can place, for nothing, a small parcel (**1 to 24 pixels**, always below the smallest paid one, **land only**). The gift is **precarious**: a paid parcel that touches it **covers** it, whole, and the free one stays in the archive's history. Everything is decided by PostgreSQL; the application only asks.

* **Data.** `parcels.tier` (`paid` | `free`), `covered_at`, `covered_by`, status `covered`. A free parcel is active at once (no order, no payment). Check constraints: paid ≥ 25 px, free ≤ 24 px and land.
* **A free parcel never blocks a purchase.** The "no overlap" exclusion constraints of the paid side only look at paid parcels (`tier = 'paid'`); free parcels have their own (`parcels_no_overlap_free`). `px_is_area_free` stays the *paid-side* question (free parcels do not count); `px_is_area_free_of_all` is the *free-side* one (nothing at all may be there: a paid or free parcel, an order being paid, a collecting project).
* **Covering is a trigger** (`px_cover_free_parcels`, after insert / update of status): whatever the path that makes a paid *land* parcel active (an order paid, a group project funded, any future one), every active free parcel whose rectangle it touches (a single shared pixel is enough) becomes `covered`, with the date and the covering parcel; a creation of it still waiting for moderation leaves the queue. So **what is on the map never overlaps** (tiles, rasters and hit-testing need no z-order). Covering is final: refunding the covering parcel does not bring the free one back. A paid *water* parcel covers nothing (it owns other pixels).
* **Placing** (`px_place_free_parcel`, called by `POST /api/free-parcel`): the edition is open, the window (`free_parcels_days` from the opening, 60), the cap (`free_parcels_cap`, 5 000 placements ever), the switch (`free_parcels_open`), the quota (**one standing at a time, `free_lifetime_max` (3) placements in all**; a parcel given back after a failed upload does not count), the land share (as a paid land parcel: the server counts the land pixels), the overlaps (under the tile lock). `px_free_status(user)` answers the site and the account in one place. The **verified e-mail** is checked by the route (`SessionUser.emailConfirmed`: Supabase's flag; the development sign-in has none and counts as confirmed).
* **Counters.** `px_public_stats`: *sold* pixels / parcels / owners count **paid parcels only**; `free_parcels` / `free_pixels` apart ("+ N free imprints" under the counter).
* **The map.** Tiles carry a 9th element (`free`). The engine's selection ignores free parcels for a purchase (it shows how many the purchase will cover, `onSelectionCovers`) and counts every parcel as blocking while a free imprint is being placed (`setFreeMode`). The buy panel offers free sizes (1×1 … 4×6), says **Free** instead of a price, hides the group-project button, and explains why a small size is refused when the account has used its turns. `CheckoutDialog` has a third mode, `free` (same editor, no payment, then the archive page of the new imprint).
* **After the covering.** The permanent address of a covered imprint (`/p/<code>`) leads to its archive page (`/archive/<code>`), which says "covered on …" and keeps the creation readable; the account page tells its owner (*Recent news*, 14 days) and offers to place another one; "my parcels" lists it with its date. **Known limit:** covered imprints are not in the closing snapshot nor in the export (they are in the database and on the site); adding them as a separate file of the export is a small follow-up if the lawyer or the owner wants them kept off-site.
* **Settings** (`/admin/settings`, audited): the switch, the window in days, the cap, the biggest free size (≤ 24), the placements per account (≤ 10). **The free period can be ended by an administrator at any time**; what is already placed stays until covered or until the closing, when it is frozen and archived like the rest.
* **Tests.** `tests/db/free-parcels.test.ts` (16: size, land, quota, overlaps, covering by a corner / several / water / any path, finality, switch, window, cap, edition, settings), `tests/unit/free.test.ts`, `tests/e2e/map-free-parcels.spec.ts` (the API end to end with a purchase that covers it, the panel and the dialog, the back-office switch).

### 3j bis. Illustration parcels (migration 24) — a third tier, owned by nobody

Decorative pictures that dress the map (the 100 hand-drawn "world heritage" ones: historic places, cultures, food, music, science, today's world), **placed by the site's owner with the demonstration tool**, not by a visitor. `parcels.tier = 'illustration'`: **25 to 2 500 pixels (up to 50 × 50), land only**. They follow the rules of the free parcels where it matters — **a paid parcel that touches one covers it, whole and for good** (the same trigger, `px_cover_free_parcels`; they never overlap a free parcel or each other, `parcels_no_overlap_free`; nobody can place a free parcel over one) — and differ where it matters: **no author** (they belong to ONE technical account, `image_illustration`, nobody can sign in to it, `lib/illustration.ts`; the card, the archive page, the `/p/` page, the share title and the share image say **"Illustration image"** / **"Image d'illustration"**; the account has no profile page, `/u/image_illustration` is a 404) and **counted nowhere** (not as sold pixels, parcels, owners, free imprints, nor as "published creations" in `px_public_stats`; no turn of the free period is used; **absent from the lists of people's creations** — Discover, the latest, the most talked about, "recently archived" — **and from the likes rankings**, whoever liked them). On the map's tiles they carry the same "not paid" flag as the free ones (`(tier <> 'paid') as free`), so the buy panel says how many "free or illustration parcels" a purchase would cover. **They are meant to stay when the site opens**: `demo:clear` removes the demonstration accounts and leaves them; `demo:clear --illustrations` removes them (parcels, files, technical account). They are in the closing archive like every visible parcel (author `image_illustration`). Tests: `tests/db/illustration-parcels.test.ts`, `tests/db/demo-heritage.test.ts`, `tests/e2e/map-illustration.spec.ts`.

## 3c. Fund it together (group projects)

A parcel that **several people pay for** (plan and decisions: `PLAN_FINANCEMENT_COLLECTIF.md`). **Built: the project and its moderation (step 1), the public pages, the contributions, the purchase of the parcel when the goal is reached, and the refunds (steps 2 and 3).** The map display (step 4) is built too; the real Stripe test (step 5) comes when Stripe is possible. Payments stay simulated (`STRIPE_MOCK`) until you approve Stripe.

* **The creator** picks a big spot (at least `campaign_min_area`, default 10 000 px), clicks **"Fund it together"** in the buy panel, designs in the **same editor** as a purchase, then gives a title, a description and a duration (**7, 14 or 30 days**) and sends the project to moderation (`POST /api/campaigns`). **Nothing is paid and nothing is held.** The server checks the rectangle and the creation like a purchase does, and **PostgreSQL prices the parcel** (`px_create_campaign`, the same settings and land/water rules as `px_start_order`): that is the goal, frozen in `campaigns.goal_cents`, in the creator's currency (euro in the euro area, dollar elsewhere).
* **One active project per creator** (`pending` or `open`): a partial unique index is the guarantee, the function gives the clean error `px_campaign_already_active`. A refused, withdrawn or finished project frees the creator.
* **A moderator decides** (`/admin/campaigns`, `px_review_campaign`, journalled in `audit_logs`). *Approve*: the zone is **held until the deadline** — a `reserved` parcel owned by the creator plus a `held` reservation without an order, so the existing overlap guarantee and the "someone is reserving this area" message work unchanged — and the creation becomes the parcel's first **approved** version, **published only when the parcel is paid for** (the moderator has seen it: no second review). If the zone was taken while the project waited, approval fails cleanly (`px_parcel_unavailable`) and the project stays pending, to be refused with a reason. *Reject*: needs a reason, which the creator reads in *My group projects* (`/account/campaigns`).
* **Withdrawing** (`px_cancel_campaign`, from the account page): a pending project is simply cancelled; an open one gives its zone back at once. **Time running out**: the maintenance job (`px_expire_campaigns`, called by `runMaintenance` and harmless if the migration is missing) closes an open project past its deadline and releases its zone. With contributions, closing also refunds them (see below).
* **The creation of a project** is stored as sent under `campaigns/<user>/…` and served only to its creator and to the staff (`GET /api/campaigns/:id/image`, never cached); the public gets pictures with the list, in step 2. The tables are server-only (RLS on, nothing granted to the browser's roles).
* **The public pages** (`/projects`, `/projects/<code>`; footer, Discover and the buy panel link to them). The list shows what is collecting (sort: ending soon / newest / most funded) and what was funded; a project page shows its creation (public once open, in three blues for the water), its goal, the progress bar, the number of contributors, the time left, and the form to chip in. **Contributions are anonymous**: only the total and the number of people are public (`lib/data/campaigns.ts → PublicCampaign` has no contributor field; an e2e test reads the pages signed out and looks for the contributors' names).
* **Contributing** (`POST /api/campaigns/:id/contribute`, `lib/stripe/contributions.ts`, migration 18). The amount is a *request*: `px_start_contribution` checks it in PostgreSQL — at least `campaign_min_contribution_cents` (except the very last bit of the goal), at most what is still missing, and never leaving less than 50 cents (a card cannot pay less, so the goal could never be completed). It holds that share for the reservation delay (like unpaid pixels), counted under a lock on the project, so **the goal is never exceeded**, however many people pay at the same time (a 24-people rush and a 5-people simultaneous payment are tested). One payment in progress per person and project. Then a Stripe Checkout Session is opened (simulated page `/dev/checkout/<id>` in development), in the project's currency.
* **A payment arrives** only through the verified webhook (or the reconciliation, which asks Stripe): `px_fulfill_contribution` checks amount and currency, that the project is still open and not past its deadline, and that the goal is not exceeded; otherwise the payment is marked `refund_required` and refunded automatically. When the paid total reaches the goal, **in the same transaction** `px_complete_campaign` makes the parcel the creator's (active, creation published, hold converted); the parcel then appears on the map.
* **Refunds.** A project that ends unfunded (deadline: maintenance job, `px_expire_campaigns`; or withdrawn by its creator) is closed by `px_close_campaign`: its zone is released, payments in progress end, every paid contribution becomes `refund_required` — in the same transaction. The application then refunds them (`refundDueContributions`, right after a withdrawal and on every maintenance run, idempotency key `auto_refund_contribution_<id>`, retried until Stripe's `charge.refunded` confirms; in the simulated mode the refund is confirmed on the spot). A refund or a lost dispute on a project that is **already funded** does not take the parcel away: it is journalled and raises an alert for a human to decide. Disputes: a disputed contribution still counts until it is lost.
* **On the map** (`lib/map/projects.ts` pure and unit-tested; `MapEngine.drawProjects`; `GET /api/map/projects`; `ProjectMapCard`). The projects that are collecting are drawn **over everything else** in the map's overlays: a hatched orange zone with a progress bar along its bottom edge once it is at least 14 px across on the screen, a **pin** (a disc with its progress as an arc) while it is a speck, so that it can still be found when the map is zoomed out. A click opens a small card (picture, title, progress, time left, "See the project"); a parcel always wins over a project under the click; while **buying** the zones are still drawn but a click places a parcel (the server says the zone is being held). The hit area of a speck is grown to 22 px so a finger can find it. **Cheap by construction**: solid lines (no dashes), only the visible part of a zone is filled, a flat tint instead of the pattern on a machine that struggles (`slowUntil` / little memory), nothing at all when there is no project; measured with a 6× slower CPU: no change at the world view, +1 to 2 ms for a project bigger than the screen, +5 ms for 300 projects in view at once (the list is capped at 300). The list is public, cached 30 s, refreshed every minute, **empty on any trouble** (missing migration, world ended), and holds nothing about who paid or who made it.
* **Settings** (admin): `campaign_min_area` (≥ 25) and `campaign_min_contribution_cents` (≥ 50; used from step 2). The durations are fixed (7, 14, 30) in `lib/campaign.ts` and in a CHECK of the table.
* **A held zone is not a sold one**: it does not count in the public counters, and it is not drawn on the map (the map shows what is active).

### What the people involved are told, and what the staff sees

* **Account page — "Recent news"** (`lib/data/news.ts`): the moderators' decision on one's project (approved with its end date, refused with the reason), a project funded (link to the parcel) or ended without its goal (everybody refunded), and the new comments on one's parcels this week. Time-based (14 days for projects, 7 for comments), so nothing needs marking as read; it never breaks the page (an error is logged and the card is simply absent). No e-mail is sent by the site itself yet.
* **Admin dashboard** (`campaignStats`): projects to review, projects collecting, contribution refunds due (lit when above zero), and, **per currency**, the money of funded projects and of those still collecting. The money of group projects is **not** in the order revenue: it counts as revenue once the parcel is bought. Soft-failing like the news (the tiles are absent if the migrations are missing).
* **Admin comments** (`/admin/comments`): the latest comments (visible or removed), with the author, the parcel, its owner, and a removal button with a reason (`remove_comment`, journalled).

## 4. Modules

* `lib/grid` — pure geometry/pricing shared by client and server (tested exhaustively).
* `lib/db` — `pg` pool, transactions with deadlock retry. All business writes call `px_*` SQL functions.
* `lib/auth` — Supabase SSR session (production) or a signed dev cookie (development only, impossible in production).
* `lib/stripe` — checkout creation, event handling (idempotency ledger), reconciliation, auto-refund.
* `lib/campaign.ts`, `lib/data/campaigns.ts` — group projects ("Fund it together"): durations and states; the creator's and the moderators' read models.
* `lib/collab.ts` — drawing together: state/delta reads, validated paint batches, snapshot publishing.
* `lib/images` — content sniffing, decompression-bomb guard, canonical PNG re-encode, average colour, hash.
* `lib/storage` — private object store: Supabase Storage in production, local files in development.
* `lib/rate-limit` — PostgreSQL fixed-window counters shared by all serverless instances.
* `lib/data` — read models (tiles, stats with cache + tag invalidation, parcels, discovery, admin).

## 5. Internationalisation

All user-facing text lives in `src/messages/<locale>.json`; a unit test enforces identical keys and placeholders between
languages. English is the default (served at `/`), French at `/fr`. To add a language: create `src/messages/xx.json`, add
`"xx"` to `src/i18n/routing.ts`. Prices and numbers use `Intl` for the active locale; country names use `Intl.DisplayNames`.

## 6. Public statistics

`px_public_stats()` computes sold pixels, parcels, owners and published creations from real rows (reservations are *not*
counted as sales). The result is cached 15 s (`unstable_cache`, tag `stats`) and invalidated after every payment/admin
action. If the database is unreachable the UI says so rather than showing a number.

## 7. Known limits / next steps

* Raster tiles are generated on demand (see scale-out path above).
* Sitemap is capped at 45 000 parcels per file; switch to `generateSitemaps()` beyond that.
* Email notifications (purchase confirmation, moderation outcome) rely on Stripe receipts / Supabase Auth emails for now.
* Parcel transfer/resale is deliberately out of scope for v1.
